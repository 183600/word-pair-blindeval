## 回答 A

先说结论：**不训练模型，想“通用大幅提升”基本不现实；但在具体任务上，用“上下文工程 + 检索 + 工具 + 验证/投票 + 路由/缓存”组合，常常能低成本显著提升。**关键是别只调 prompt，而是把 LLM 放进一个可验证、可检索、可升级的工作流里。

## 按 ROI 从高到低排序

### 1. 提示与输出契约：几乎零成本
不要只写“请仔细思考”。要写成任务契约：

- 明确角色、目标、输入、输出格式、边界条件
- 给 2～5 个高质量 few-shot，最好按输入动态检索相似样例
- 强制结构化输出：JSON Schema / 表格 / 固定字段
- 加检查清单：是否引用来源、是否遗漏字段、是否计算、是否需拒答
- 对不确定问题要求“先检索/先问澄清/标注不确定”，禁止编造

收益：格式稳定性、抽取准确率、客服/文档处理提升明显。  
注意：单纯“深呼吸/你是专家”这类技巧提升有限，不要期待质变。

### 2. RAG：知识密集任务首选
如果任务依赖外部知识，RAG 通常是低成本最大增量：

- 混合检索：BM25 + 向量检索
- rerank：用现成 reranker 重排 top-k
- 查询改写/多查询：把用户问题改写成多个检索 query
- 上下文压缩：只放相关片段，避免长上下文稀释
- 引用来源 + 无依据拒答
- chunk 按标题/段落切，不要盲目固定长度

适用：企业知识库、客服、文档问答、政策/合同/产品资料。  
关键：**RAG 的效果 70% 取决于检索和切分，不是 prompt。**

### 3. 工具调用：让模型“算、查、执行”
对数学、代码、实时信息、数据库查询，工具比模型硬想可靠得多：

- 计算器/代码执行
- 搜索引擎/浏览器
- 数据库/API/CRM/订单系统
- 代码 lint、单元测试、schema 校验

典型模式：模型负责理解与规划，工具负责事实与执行，模型负责总结。  
这通常比换更大模型更便宜。

### 4. 推理时计算：投票、验证、升级
适合答案可验证或可比较的任务：

- **Self-consistency**：多采样几次，多数投票。适合数学、分类、抽取。
- **Best-of-N + verifier**：生成 3～5 个答案，用规则/小模型/强模型打分选最好。
- **外部验证器**：JSON schema、正则、单元测试、引用核查、业务规则。
- **级联路由**：小模型先做，置信度低/验证失败再升级大模型。
- **多模型投票/辩论/MoA**：效果可能好，但成本高，适合高价值低频任务。

注意：没有外部反馈的“自我反思/自我批评”经常无效甚至变差；要有检索、工具、规则或更强 verifier 才有意义。

### 5. 路由、缓存、降级：成本换性能
- 简单任务走小模型，复杂任务走大模型
- 用分类器/规则/置信度判断是否升级
- 语义缓存高频问题答案
- 失败时 fallback 到更强模型或人工
- 对稳定任务缓存 few-shot 示例和检索结果

这能在总成本不大增的情况下，把预算集中到难题上。

### 6. 结构化解码与参数调优
如果 API/框架支持：

- JSON Schema / grammar-constrained decoding
- stop sequences
- temperature/top_p 按任务调低
- logit_bias 控制禁用词/格式
- 最大 token 控制，避免跑偏

对抽取、分类、API 调用、表单填写很实用。

### 7. 上下文工程与记忆
- 系统提示精简，别塞矛盾规则
- 长对话做滚动摘要
- 重要信息放上下文前部和尾部
- 用户偏好/历史/业务状态存外部记忆
- 不要把长上下文当 RAG 替代品；无关内容会干扰

### 8. 工作流化：Plan → Execute → Verify
把一次性问答改成流程：

1. 解析任务/澄清
2. 检索或调用工具
3. 生成候选
4. 规则/工具/第二模型验证
5. 不通过则重试或升级
6. 输出附引用/置信度

比“让一个 agent 无限循环”更稳、更便宜。Agent 要限制步数、预算和工具权限。

## 推荐的最小低成本组合

如果只能做一套，建议：

**任务模板 + 动态 few-shot + 混合检索/rerank + JSON Schema + 工具校验 + 2～3 候选投票 + 失败升级大模型 + 语义缓存 + 小评测集**

适用大多数企业任务。预期不是“通用 IQ 大涨”，而是在目标任务上显著减少幻觉、格式错误和遗漏。

## 分场景配方

- **企业知识问答**：混合检索 + rerank + 引用 + 无依据拒答 + 高频缓存 + 难题升级大模型。
- **代码助手**：代码执行 + 单元测试 + lint + 多候选 + 失败重试。
- **数学/数据计算**：代码解释器/计算器 + 自洽投票 + 结果校验。
- **信息抽取/表单**：JSON Schema + few-shot + 正则/业务规则校验 + 低 temperature。
- **客服**：意图路由 + 知识库 RAG + 工具查订单 + 敏感操作人工确认。
- **高价值低频决策**：多模型投票/辩论/MoA + 强 verifier，但控制调用次数。

## 不要踩的坑

- 只加“你是专家/深呼吸”就期待大幅提升
- 盲目塞超长上下文
- 没有验证器却让模型反复自我反思
- RAG 只做向量检索、不 rerank、不引用
- 过度 Agent 化，步数多、成本高、错误累积
- 不建评测集，靠感觉调 prompt

## 落地顺序

1. 建 50～200 条真实任务评测集，定义准确率/幻觉率/格式合格率/延迟/成本。
2. 先做提示契约和结构化输出。
3. 知识任务加混合检索 + rerank + 引用。
4. 可执行任务加工具和规则验证。
5. 加 2～3 候选投票与失败升级。
6. 加缓存和路由。
7. 每周做错误分析，只优化 top 错误类型。

一句话：**低成本提升现有 LLM 的核心不是“更神 prompt”，而是“检索给事实、工具给执行、schema 给格式、验证器给质量、路由给成本”。**

## 回答 B

低成本、无需额外训练提升现有 LLM 性能，核心不是“改模型权重”，而是“改推理系统”。可归纳为：**检索给证据、规划降难度、反思做校验、工具补能力、路由省成本、投票提稳定、约束保格式、评估防回退**。

### 1. 高质量 RAG 闭环
低成本最有效的方向之一。不要只做“向量检索 + 拼接上下文”，而应做：
- 查询改写 / 扩展 / 多路召回
- 向量检索 + 关键词检索混合
- 重排 rerank
- 文档清洗、分块、元数据过滤、时效过滤
- 上下文压缩、去重、引用溯源
- 要求模型“无证据则拒答或标注不确定”

适合：知识问答、客服、企业内部文档、报告生成。

### 2. 推理时计算扩展
不需要训练，只增加推理调用：
- 多采样 + 自洽投票
- Best-of-N：生成多个候选，用规则、小模型、embedding 或 LLM judge 打分
- 草稿—批评—修订
- 多角色辩论后裁决
- 让模型先给答案，再自查证据和反例

注意：自我反思可能放大错误，最好接外部证据、代码执行或独立验证器。

### 3. 任务分解 + 工作流
把复杂任务拆成：
- 计划 → 执行 → 检查
- 子任务路由
- ReAct：观察—行动—再观察
- 函数调用、SQL、代码解释器、计算器
- 自动生成中间检查点

这比让一个 prompt 一次解决所有问题更稳。

### 4. 动态 Few-shot 与提示优化
无需微调权重，也可用数据优化提示：
- 检索相似示例做动态 few-shot
- 固定结构化模板：角色、任务、约束、输入、输出 schema、检查清单
- 用小规模评测集自动搜索 prompt
- 对失败样本做错误分类，针对性改提示

这属于“提示/上下文优化”，不是训练模型。

### 5. 模型路由与级联
- 简单任务走小模型，复杂任务升级大模型
- 低置信度、格式错误、验证失败时自动升级
- 多模型交叉验证，关键任务用不同模型投票
- 语义缓存高频问题，节省预算给困难样本

这样总成本可控，但难例体验更好。

### 6. 输出约束与自动验证
- JSON Schema / 语法约束 / 模板填充
- 参数校验、单元测试、正则检查
- 代码执行、SQL 试运行、单位换算检查
- 引用必须可追溯
- 失败后自动修复循环，仍失败则回退

对抽取、表格、代码、API 调用类任务提升明显。

### 7. 上下文工程与记忆
- 长上下文不是越长越好：摘要、滑窗、递归压缩
- 实体链接、关系抽取、时间归一
- 会话记忆与用户偏好分离
- 只放与当前任务强相关的证据
- 对冲突信息显式标注来源和时间

### 8. 建立小评测集与回归测试
先不要追求“万能提升”。选 50～200 个真实任务样本：
- 记录基线
- 按错误类型分类：知识缺失、推理错、格式错、遗漏、幻觉、工具错
- 每次改 prompt / RAG / 路由都跑回归
- 用 A/B 测试和人工抽检确认是否真的提升

没有评测，“大幅提升”很容易变成感觉提升。

### 推荐落地顺序
1. 建 50～200 条任务评测集  
2. 上 RAG + rerank + 引用  
3. 加结构化输出 + 校验器 + 自动修复  
4. 对难任务加多候选投票 / 草稿修订  
5. 加小模型到大模型的级联路由  
6. 用失败样本做 prompt 和 few-shot 优化  
7. 最后再考虑多代理、辩论、ToT 等更贵方案  

一句话：**不训练模型也能显著提升，但提升来自“检索、验证、分解、路由、约束、评测”组成的系统；不要单靠一个神奇 prompt。**
