## 回答 A

先给结论：**不训练模型时，提升来自“推理系统工程”：更好的上下文、检索、工具、验证、采样与路由**。其中 ROI 最高的是：**小评测集 + 提示契约 + RAG/工具 + 自一致性/验证器 + 缓存与路由**。但“性能”必须按任务定义；没有一种方法在所有任务上都大幅提升。

## 1. 先建一个 30–100 条的小评测集
不做训练也可以做“数据驱动调优”。收集真实请求，定义指标：正确率、引用准确率、格式合规率、延迟、token 成本。每加一招都跑同一套 eval，否则很容易“感觉变好”。

## 2. 低成本高收益组合，按优先级

### ① 提示契约 + Few-shot + 结构化输出
强制模型输出 JSON/Markdown 模板，明确：
- 任务边界、可用信息、禁止编造
- 输出字段和校验规则
- 2–5 个高质量示例
- 不确定时如何回答/要求澄清

适合所有任务，成本几乎为 0，格式和稳定性提升明显。

### ② RAG：检索增强生成
对知识型、文档型、客服、代码库问答，**RAG 通常比换更大模型更划算**。低成本做法：
1. 查询改写/多查询
2. 混合检索：BM25 + 向量检索
3. 用现成 reranker 重排 top 20 → top 3–5
4. 上下文压缩：只放相关句段
5. 要求逐条引用来源
6. 检索不到就拒答或澄清

不需要训练 LLM；embedding/reranker 用现成模型即可。

### ③ 推理时扩展：CoT、自一致性、Best-of-N + 验证器
适合数学、逻辑、代码、规划等。
- 简单题：单次回答
- 难题：采样 3–10 个答案，投票或让验证器选最佳
- 代码/数学：用执行器、单测、计算器验证
- 让 LLM 自己先写检查清单，再回答，再按清单自检

注意：Self-Consistency 成本是 N 倍。低成本策略是**只对高不确定/高价值 query 启用**，用 logprobs、规则或小模型判断难度。

### ④ 工具调用 / ReAct
让模型调用搜索、计算器、数据库、代码解释器、业务 API、单测。对事实、计算、实时信息、代码执行类任务，工具带来的是“质变”，不是单纯 prompt 能比。

### ⑤ 验证器与重试
生成后做：
- JSON Schema 校验
- 正则/业务规则校验
- 引用是否支持结论
- 代码是否通过测试
- 多候选交叉验证

失败时把错误信息回填给模型重试 1–2 次。成本低，可靠性提升大。

### ⑥ 模型路由 / 级联 / 小模型预筛
不是所有请求都值得用大模型：
- 小模型处理简单分类、抽取、改写、格式化
- 大模型只处理难题或小模型置信度低的请求
- 多模型投票/辩论只用于高风险请求

这能在总成本不大涨的情况下提升平均质量。

### ⑦ 缓存与上下文管理
- 语义缓存：相似问题直接命中历史答案
- KV cache、prompt caching
- 上下文裁剪/摘要，避免无关长文档
- 批处理、并行请求
- 量化/更小模型服务简单步骤

这些主要降成本，为高价值请求释放预算。

## 3. 一个可直接落地的低成本架构

```text
用户问题
→ 语义缓存命中？→ 返回
→ 查询改写
→ 混合检索 + rerank（需要知识时）
→ 难度/置信度判断
   ├─ 简单：单次 LLM + 结构化输出
   └─ 困难：多候选采样 + 验证器/工具/投票
→ Schema/规则/引用校验
   ├─ 失败：带错误信息重试 1–2 次
   └─ 成功：返回并缓存
```

核心原则：**简单请求走便宜路径，困难请求才增加推理计算**。

## 4. 不同任务的最优组合

| 任务 | 首选方案 |
|---|---|
| 文档/知识问答 | RAG + 查询改写 + rerank + 引用 |
| 客服/业务流程 | 提示契约 + 结构化输出 + 工具 API + 校验重试 |
| 数学/逻辑 | CoT + Self-Consistency + 计算器/验证器 |
| 代码 | 检索相关代码 + 代码解释器 + 单测 + Best-of-N |
| 信息抽取 | Few-shot + JSON Schema + 规则校验 |
| 高风险决策 | 多模型投票/辩论 + 外部证据 + 人工复核 |
| 长文档 | 分块检索 + 摘要树 + 上下文压缩 |

## 5. 推荐实施顺序
1. **建 eval 集**，记录 baseline。
2. **改提示契约 + 结构化输出**：几乎零成本。
3. **加 RAG/工具**：按任务决定，通常收益最大。
4. **加验证器与重试**：提升可靠性。
5. **对难题加自一致性/Best-of-N**：用路由控制成本。
6. **加缓存、模型路由、上下文压缩**：把成本压回来。
7. **持续看指标**：准确率、格式合规率、引用准确率、P95 延迟、每请求成本。

## 6. 注意事项
- “大幅提升”通常有任务边界：RAG 对知识问答可很大；工具对计算/代码可很大；提示工程对格式和稳定性提升大，但不能让模型学会新知识。
- 多采样、多 agent、反思会显著增加 token 和延迟，必须做**自适应计算**。
- RAG 的瓶颈常在检索和切分，不在 LLM。
- 自检/反思可能“自信地犯错”，最好有外部验证器或规则。
- 不要一次性堆满所有技巧；逐项 ablation，保留有效组合。

一句话：**用评测集找短板；知识问题上 RAG，计算/实时问题上工具，推理问题上采样+验证，成本问题用路由和缓存。** 这是当前不额外训练、低成本提升现有 LLM 最稳的路线。

## 回答 B

低成本、不额外训练现有 LLM 而显著提升性能，核心是：**不改模型参数，改“输入、上下文、外部知识、调用流程、验证机制和工程策略”**。可按下面优先级落地。

### 1. 先建小型评测集与错误分类
用 50～300 条真实任务做回归集，记录错误类型：知识缺失、格式错误、计算错误、幻觉、拒答不当、指令理解偏差等。  
作用：避免“感觉变好”，让后续优化可量化。

### 2. 提示模板 + 结构化输出 + 校验重试
把任务写成稳定模板：角色、目标、输入、约束、输出格式、拒答边界、示例。强制 JSON/函数签名/表格输出，解析失败自动重试或修复。  
这是最低成本、最高确定性的提升之一。

### 3. 做轻量 RAG：混合检索 + 重排 + 引用
文档分块、元数据过滤、BM25+向量混合召回，查询改写，候选重排，要求答案引用证据。知识更新只更新库，不训练模型。  
对知识问答、客服、企业文档、政策法规类效果通常最明显。

### 4. 动态少样本与自动提示优化
从案例库检索相似成功样例，动态拼入 few-shot；维护模板库并版本化。可用 LLM 生成候选提示，再用回归集筛选。  
不需要训练，只需小规模实验。

### 5. 自洽投票、多草稿与轻量评审
对高价值任务采样多个答案，用规则、评分卡、小模型或 LLM 裁判做重排/投票；高风险任务再人工抽检。  
注意只对难题或高价值任务启用，否则成本上升。

### 6. 工具调用与程序化编排
把计算、搜索、数据库查询、代码执行、文件解析交给工具；模型负责计划、参数生成和结果解释。函数参数要 schema 校验、超时降级、失败重试。  
对数学、时效信息、表格、代码、业务系统查询提升大。

### 7. 路由与级联：简单问题走便宜路径
先做任务分类/难度估计/风险分级：简单任务走小模型、缓存或模板；复杂任务升级大模型或多步流程。配合语义缓存、前缀缓存、结果复用。  
这是低成本“大幅提效”的关键工程杠杆。

### 8. 上下文压缩与会话记忆
长文档先摘要/关键句抽取/实体关系抽取；会话用滚动摘要；只放必要上下文，减少噪声和 token。  
可同时提升准确率、延迟和成本。

### 9. 验证器与护栏：先答后验
输出后做事实核查、引用溯源、幻觉检测、正则/白名单过滤、敏感与合规检查；不确定时拒答或转人工。  
对生产环境尤其必要。

### 10. 轻量多智能体只在复杂任务启用
角色分工、批评修正、评审辩论适合复杂推理/写作/代码审查，但成本高。建议只对复杂任务开启 2～3 个角色，不要全量多代理。

### 最小落地组合
如果只做一版低成本方案，建议：  
**小型评测集 → 提示模板+结构化输出 → 混合检索 RAG → 语义缓存+路由 → 输出校验/重试 → 高价值任务自洽投票。**  
这套组合通常能在不训练模型的前提下，对知识问答、客服、文档处理、业务查询、结构化输出等任务带来明显提升；对需要全新技能或大量隐性知识的任务，提升有限，不能替代微调或继续预训练。
