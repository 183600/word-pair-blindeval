## 回答 A

结论先说：**不改权重、不训练，想让现有 LLM “大幅提升”，最有效的不是堆提示词，而是把模型放进一个增强系统：检索补知识、工具补能力、验证补可靠性、路由补成本、缓存补效率。**  
对**知识问答、实时信息、计算/数据、写代码、格式约束、工具操作**类任务，提升可以很大；对**纯创作、复杂开放推理**，提升通常中等，且要靠增加推理计算换效果。

## 按性价比排序的方法

| 方法 | 适合任务 | 效果 | 成本 |
|---|---|---:|---:|
| RAG：查询改写 + 混合检索 + rerank + 上下文压缩 | 企业知识、文档问答、最新信息 | 很高 | 低-中 |
| 工具调用：搜索、计算器、代码执行、数据库/API | 数学、数据、实时、业务操作 | 很高 | 低-中 |
| 结构化输出 + 约束解码 JSON Schema | 信息抽取、表单、API 参数 | 高 | 低 |
| 验证器/自检/交叉检查 | 事实、代码、数学、关键决策 | 高 | 中 |
| 选择性 self-consistency / best-of-N | 难题、高价值问题 | 高 | 中-高 |
| 模型级联路由：小模型先答，难题升级大模型 | 大规模服务降本 | 高 | 低 |
| 上下文工程：任务拆解、示例、检查清单、输出规范 | 大多数任务 | 中-高 | 低 |
| Agent 工作流：计划-执行-观察-修正 | 多步任务、工具任务 | 中-高 | 中 |
| 缓存/语义缓存/前缀缓存 | 重复查询、长系统提示 | 降本提速 | 低 |
| 用评测集自动优化 prompt/few-shot | 固定业务任务 | 中-高 | 低-中 |

## 最推荐的最小增强栈

一个低成本、无需训练的实用流水线：

1. **建 50–200 条真实评测集**  
   没有评测就不要谈提升。记录准确率、格式合规率、幻觉率、延迟、成本。

2. **查询改写 + RAG**  
   用户问题先改写/扩展；用 BM25 + 向量混合检索；小 reranker 重排；只放最相关片段；要求引用来源。  
   适合：知识库、客服、文档、政策、产品问答。

3. **强制结构化输出**  
   用 JSON Schema、函数调用、语法约束解码，减少格式错误和胡编字段。  
   适合：抽取、分类、工单、API 调用。

4. **给模型工具，而不是让它脑算**  
   数学用计算器/代码执行；实时信息用搜索；业务数据查数据库；代码跑单元测试。  
   原则：**能验证的交给外部系统，LLM 只负责理解、规划和生成参数。**

5. **加一个验证/修正环节**  
   例如：答案生成后让模型按检查清单自检；关键事实要求引用；代码必须过测试；JSON 必须过 schema；低置信度触发重试。  
   不要盲信“自我反思”，最好接外部验证器。

6. **只对难题做推理扩展**  
   简单题单次回答；难题用 3–5 次采样投票、best-of-N + verifier，或升级到大模型。  
   这比所有请求都多采样便宜很多。

7. **模型级联路由**  
   小模型先处理；规则/置信度/验证器失败时再调大模型。  
   典型策略：80% 简单请求走小模型，20% 难题走强模型。

8. **缓存和上下文压缩**  
   语义缓存高频问题；系统提示固定以利用前缀缓存；RAG 只放 top 3–5 片段并压缩；减少无关上下文。

## 可直接套用的系统形态

用户问题  
→ 查询改写  
→ 混合检索 + rerank  
→ 上下文压缩  
→ LLM 按结构化格式生成  
→ 必要时调用工具/代码  
→ 验证器检查事实、格式、测试  
→ 失败或低置信度则 self-consistency 或升级大模型  
→ 缓存结果

## 关键提示词/上下文技巧

不要再只写“请一步步思考”。更有用的是：

- 明确角色、目标、输入、输出格式；
- 给 2–5 个高质量 few-shot；
- 要求先列假设和缺失信息；
- 把复杂任务拆成子问题；
- 提供检查清单；
- 要求引用证据；
- 输出 schema；
- 对不确定信息明确说“不知道/需查证”；
- 对代码要求“先写测试，再实现，再根据测试修正”。

## 哪些能“大幅提升”，哪些不能

提升明显的场景：

- 私域知识/最新知识问答：RAG；
- 数学、统计、数据处理：代码解释器/计算器；
- 实时信息：搜索工具；
- 表单抽取、API 调用：结构化输出；
- 代码：执行测试 + 修复循环；
- 高风险事实任务：检索 + 引用 + 验证器；
- 大规模服务：小模型 + 路由 + 缓存。

提升有限的场景：

- 模型本身不会的复杂推理；
- 长链条创造性任务；
- 没有外部知识又要求事实准确；
- 只靠“换个提示词”就想全面提升。

## 低成本注意事项

- **不要全量多采样**，只对难题做。
- **RAG top-k 不要太大**，重排后保留少量高相关片段。
- **验证器优先用规则、测试、schema、检索证据**，别只靠 LLM judge。
- **优先小模型路由 + 大模型兜底**。
- **先做评测集和错误分析**，否则容易加了一堆花活但没有净收益。
- 推理扩展、多模型投票本质是“用推理成本换性能”，不是免费提升；低成本靠选择性触发。

一句话版本：**用 RAG 补知识，用工具补计算和操作，用结构化输出补格式，用验证器补可靠性，用路由和缓存控成本。** 这通常是不训练模型时提升现有 LLM 最有效的组合拳。

## 回答 B

回答：**低成本、不额外训练，如何尽量大幅提升现有LLM性能？**

先说结论：**不训练模型，也能显著提升，但主要靠“系统编排 + 检索 + 工具 + 验证 + 评测”**。在知识密集、客服、文档问答、数据分析、流程自动化、代码等任务上，提升往往很明显；通用创意写作提升有限。不要只改一句提示词，要做轻量LLM应用系统。

### 推荐优先级：先做这5件事

1. **建小型评测集**
   - 收集50–200条真实任务，写清标准答案或评分规则。
   - 先测基线，之后每改一项都回归测试。
   - 没有评测，所谓“大幅提升”不可验证。

2. **RAG检索增强**
   - 适用于企业知识、文档、FAQ、政策、产品资料。
   - 用“关键词检索 + 向量检索”的混合检索，再加 reranker 重排。
   - 做查询改写、分块优化、上下文压缩、引用溯源、权限过滤。
   - 这是不训练LLM时通常收益最大的方向。

3. **工具调用 + 结果验证**
   - 让LLM调用搜索、数据库、计算器、代码执行、业务API、规则校验器。
   - 对结构化输出使用 JSON Schema/函数调用，失败自动重试。
   - 对事实、数字、日期、金额、权限做程序校验。
   - 数学/统计/表格任务优先用代码工具，不让模型硬算。

4. **推理时编排：分解—执行—校验—重写**
   - 复杂任务拆成：理解问题 → 检索资料 → 生成草稿 → 自检/交叉验证 → 修正输出。
   - 可使用自一致性：对关键问题采样多次，投票或让评审器择优，但只对高价值问题启用，控制成本。
   - 用便宜小模型做分类、抽取、摘要、初稿；难例升级给强模型。

5. **结构化提示 + 缓存 + 路由**
   - 系统提示写清角色、目标、边界、输出格式、拒答条件。
   - 动态少样本示例：按语义相似度检索最相关示例放入提示。
   - 做语义缓存、会话摘要、长期记忆，减少重复计算。
   - 按任务难度路由：简单请求走小模型，复杂请求走强模型。

### 低成本落地方案

最小可行栈：

- 现有LLM API 或本地模型
- 向量库/关键词检索：如 FAISS、BM25、pgvector、Elasticsearch
- 现成 embedding + reranker 模型，不训练
- 函数调用/工具层
- 简单工作流编排
- 日志、评测、缓存、限流

典型流程：

**用户问题 → 意图识别/难度路由 → 查询改写 → 混合检索 → 重排压缩 → LLM生成 → 工具校验/事实核查 → 结构化输出 → 失败重试/人工复核 → 日志评测**

### 场景对应策略

- **文档/客服问答**：RAG + rerank + 引用 + 拒答策略，收益最大。
- **数据分析/数学**：代码执行 + 计算器 + 校验，避免纯语言推理。
- **复杂决策/规划**：任务分解 + 多轮自检 + 评审器。
- **格式严格的业务输出**：JSON Schema + 函数调用 + 自动重试。
- **实时信息**：搜索工具 + 来源可信度排序。
- **高并发低成本**：小模型初筛 + 强模型兜底 + 缓存 + 批处理。
- **高风险场景**：规则引擎 + 人工复核 + 审计留痕。

### 关键提醒

- **“不额外训练”不等于“零工程”**；低成本是相对重新训练而言。
- 不要一上来做多智能体大系统，先做 **RAG + 工具校验 + 结构化输出 + 评测**。
- 对关键任务，**验证器比更长的提示词更重要**。
- 要监控：准确率、引用正确率、拒答率、延迟、单次成本、失败类型。
- 如果允许轻量LoRA/微调，效果可能更强；但在“不训练”约束下，优先把检索、工具和验证做好。
