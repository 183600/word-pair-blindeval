## 回答 A

低成本、不额外训练，想“大幅提升”现有LLM性能，核心不是改模型，而是做**推理时系统优化**。先限定在具体任务/场景上；通用能力全面大幅提升不现实，但在知识问答、客服、文档分析、代码、数据分析等任务上，组合下面这些方法通常效果很明显。

**核心公式：**  
**好上下文 + 外部知识 + 工具 + 多次候选 + 验证/路由 + 缓存/评估闭环**

### 1. 最高性价比：RAG检索增强
- 混合检索：BM25关键词 + 向量语义检索。
- 查询改写：多查询、HyDE、同义词扩展。
- 重排：先召回30–50条，再用rerank模型取前5条。
- 分块：300–800字，带标题、来源、权限、时间元数据。
- 强制引用证据；证据不足时回答“无法确定/需要补充信息”，显著降低幻觉。
- 上下文压缩：只放关键片段，降低token成本。

### 2. 上下文工程与提示结构
用一个稳定模板：
- 角色与目标；
- 已知信息/证据；
- 明确约束；
- 输出格式JSON或固定结构；
- 检查清单；
- 2–5个高质量few-shot示例；
- 模糊问题先追问澄清。
对复杂任务先拆解子问题，再逐项回答并组装。

### 3. 推理时增强：自洽、评审、验证
- 难题用self-consistency：生成3–5个答案投票，仅对高价值/高不确定问题启用，控制成本。
- 草稿→评审→修正，最多1–2轮。
- 用规则校验格式、数值、单位、引用、SQL/代码执行结果。
- 低置信度时追问、拒答或升级大模型。

### 4. 工具调用
让模型调用计算器、代码执行器、SQL、搜索、API、业务系统。  
原则：能计算就不要硬算，能查库就不要凭记忆，能执行验证就不要只靠语言推理。

### 5. 模型路由与级联
- 简单问题走小模型/便宜模型；
- 难题、低置信、长上下文、高风险问题升级大模型；
- 用任务分类器或置信度门槛做路由。
这能同时提升效果和降低成本。

### 6. 缓存与记忆
- 前缀缓存：固定系统提示、工具说明、长文档。
- 语义缓存：相似问题复用答案。
- 会话摘要、用户画像、长期记忆，减少重复上下文。
- 对高频查询做结果缓存，但设置时效和权限。

### 7. 评估闭环
先做50–200条黄金测试集，记录：
- 正确率、引用准确率、幻觉率、格式合格率、平均token、延迟、成本；
- 每次改prompt、检索参数、路由规则都回归测试；
- 用自动评分+人工抽检持续优化。

### 一个低成本落地架构
**查询改写 → 任务路由 → 混合检索 → 重排 → 上下文组装 → 小模型草稿 → 规则/工具/评审验证 → 低置信升级大模型 → 缓存与日志 → 评估迭代**

### 建议实施顺序
1. 先做输出结构+约束+检查清单+2–5个示例；
2. 加RAG混合检索、重排、引用和拒答；
3. 加计算/代码/SQL/搜索工具；
4. 加路由级联和缓存；
5. 只对难题加自洽投票和评审；
6. 建立黄金集和回归评估。

注意：不要一开始堆多智能体，成本高且容易不稳定。优先做确定性流水线：检索、重排、模板、验证、路由、缓存。真正要实现“大幅提升”，关键是把模型放进一个可检索、可验证、可路由、可评估的系统里，而不是只改一句提示词。

## 回答 B

可以，但先明确：**不训练权重时，提升来自“把模型放进更好的系统”**，不是靠一句神提示。效果通常来自补齐五类短板：**缺知识、缺约束、缺工具、缺验证、缺上下文管理**。低成本优先级如下。

## 1. 先做评测集和错误分析（最重要，成本最低）
不要盲调 prompt。抽 50～200 个真实任务，建小测试集，记录：
- 准确率/事实性/格式合规率
- 失败类型：没检索到、理解错、算错、格式错、幻觉、遗漏约束
- 延迟和 token 成本

没有这个，你无法知道“大幅提升”来自哪里。

## 2. 结构化提示模板：立刻见效
把系统提示改成固定结构：
1. 角色与目标
2. 输入说明
3. 必须遵守的约束
4. 可用证据/上下文
5. 输出格式（JSON Schema/表格/枚举）
6. 回答前检查清单
7. 不确定时如何处理

建议加：
- 3～5 个高质量 few-shot 示例
- “先列要点/计划，再给最终答案”
- “只基于给定证据回答，缺证据就说不知道”
- 输出后自检：格式、事实、是否遗漏约束

这是零训练、几分钟到几小时可做的第一层提升。

## 3. RAG：知识密集任务提升最大
如果任务依赖企业文档、产品资料、政策、代码库、最新信息，优先做 RAG：
- 文档清洗：去页眉页脚、表格转文本、按标题层级切分
- 分块：300～800 token，10%～20% overlap
- 混合检索：BM25 + 向量检索，各取 top 20～50
- 重排 rerank：取 top 5～8 放入上下文
- Query rewrite / 多查询：把用户问题改写成检索友好查询
- 上下文压缩：只保留相关段落，附来源
- 回答必须引用证据；证据不足时拒答或追问

低成本组合：**BM25 + 开源 embedding + 小 reranker**，通常比单纯向量检索稳。

## 4. 工具调用：解决算数、实时性、精确操作
给模型接：
- 搜索引擎/内部搜索
- 计算器/代码解释器
- 数据库/API
- 日历、订单、CRM 等业务系统
- 校验器：JSON Schema、正则、业务规则

原则：**能查就不让模型记，能算就不让模型猜，能校验就不靠模型自觉。**

## 5. 推理时扩展：不训练但增加推理算力
适合高价值、低并发任务：
- Self-consistency：同一问题采样 3～5 次，投票/选一致答案
- Best-of-N + 评分器：生成多个候选，用规则或小模型/大模型评审选最佳
- 一轮反思：让模型检查“是否遗漏约束、证据是否支持、格式是否正确”
- 计划-执行-校验：先拆步骤，再执行，再验证

注意：N 倍采样会增加成本，建议只对**高不确定性/高价值样本**启用。

## 6. 路由与级联：同时降成本和提质量
- 简单问题走小模型/缓存
- 复杂问题升级到大模型
- 低置信度、格式失败、检索不足时触发升级或重试
- 高频问题语义缓存
- 长系统提示使用 prompt caching
- 批处理离线任务

这通常能“小模型成本 + 接近大模型质量”。

## 7. 结构化输出与后处理
对业务系统尤其有效：
- 强制 JSON Schema / 函数调用
- 枚举字段限制
- 正则校验
- 失败自动重试并附错误信息
- 关键字段二次抽取/交叉验证

格式稳定性往往比换更大模型更明显。

## 8. 上下文工程
- 多轮对话做滚动摘要
- 维护实体表/任务状态机，不把所有历史塞回去
- 长期记忆用检索，不要全量拼接
- 超长上下文先压缩再回答
- 把“必须遵守的规则”放系统提示，把“证据”放用户上下文

## 9. 推荐最低成本落地组合
如果只做一套，按任务选：

- **知识问答/客服/文档分析**：结构化提示 + 混合检索 + rerank + 引用 + 证据不足拒答
- **数学/数据/报表**：代码解释器 + 计算器 + 结构化输出 + 自检
- **业务流程/表单抽取**：JSON Schema + few-shot + 规则校验 + 失败重试
- **高价值难题**：计划-执行-校验 + 3 次自洽 + 评分器
- **成本敏感应用**：小模型草稿 + 大模型兜底 + 语义缓存 + 路由

## 10. 一周落地顺序
1. 建 100 条评测集，标错误类型
2. 改结构化提示 + few-shot + 输出 Schema
3. 加 RAG 混合检索 + rerank + 引用
4. 加工具调用/校验器
5. 对高价值样本加自洽/反思
6. 加路由、缓存、重试
7. A/B 对比准确率、格式率、延迟、成本

## 现实预期
不训练可以**显著提升任务成功率**，尤其在知识密集、流程化、可验证、可工具化任务上；但它不能改变模型基础能力上限，也不能完全替代微调对领域术语、稳定风格、固定行为的收益。**最大收益通常来自：评测驱动 + RAG + 工具 + 验证器 + 结构化输出**，而不是复杂多智能体。盲目加多智能体和超长提示，常常成本上升但效果不稳。
