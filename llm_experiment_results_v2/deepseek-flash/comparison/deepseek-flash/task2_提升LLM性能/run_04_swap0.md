## 回答 A

不能靠“改一句提示词”就把所有任务大幅提升；但**不训练模型**时，收益最大的方向是：把 LLM 从“单次闭卷生成”改造成“带检索、工具、验证、路由和缓存的推理系统”。低成本的关键是：**只在必要样本上增加推理计算**。

下面按性价比排序。

## 1. 先做评测集，否则不知道是否提升
先构造 100～500 条真实任务金标准，记录：
- 准确率/通过率
- 格式合规率
- 幻觉率
- 平均 token 成本和延迟
- 失败类型

后续所有技巧都围绕失败类型上。没有评测的“提示词优化”大多是玄学。

## 2. 最高性价比：上下文与输出约束
### 结构化提示
固定角色、任务、输入、约束、输出 schema：
```text
你是...。只根据给定资料回答。
必须输出 JSON：{answer, evidence, confidence}
若资料不足，输出 insufficient=true。
```
适合抽取、分类、客服、报告生成。

### 动态 few-shot
不要固定示例，而是用向量检索选出与当前问题最相似的 3～5 个高质量示例插入提示。通常比手写长 prompt 更稳。

### 输出约束/解析器
用 JSON Schema、正则、枚举、函数调用约束输出；失败自动重试或修复。能显著降低下游系统错误。

### 上下文压缩
长文档先检索、重排、摘要，再喂给模型。避免“塞满上下文”导致注意力稀释和成本上升。

## 3. 检索增强 RAG：低成本大幅降低幻觉
最小方案：
1. 文档切块 300～800 token，带标题/来源元数据；
2. 向量检索 top 20；
3. cross-encoder/轻量 reranker 取 top 5；
4. 提示中要求引用证据；
5. 无证据时拒答。

提升点：
- **HyDE**：先让模型生成假设答案再检索；
- **多查询检索**：把问题改写成 3 个查询；
- **混合检索**：BM25 + 向量；
- **父子块**：小块检索、大块喂入；
- **引用校验**：答案中每个关键结论必须有 evidence id。

这是很多企业场景中“提升最大、训练成本最低”的手段。

## 4. 推理时增强：只在难题上多花算力
### Self-consistency
同一问题采样 3～5 次，投票选多数答案。适合数学、分类、判断。成本线性增加，所以只对高不确定样本用。

### Best-of-N + 验证器
生成多个候选，用规则/小模型/LLM verifier 打分选最优。验证器比生成器便宜很多。

### 自检与修复
流程：
1. 生成初稿；
2. 检查是否满足约束、是否有证据；
3. 只对失败项重写；
4. 再次校验。

比全量重试便宜。

### 分解任务
复杂任务拆成：计划 → 检索 → 执行 → 校验。适合多步推理、报告、数据分析。

### 多智能体/辩论谨慎用
debate、多角色评审能提升，但成本高。低成本替代：**单模型多轮自检 + 规则验证 + 小模型评审**。

## 5. 工具调用：把模型不擅长的交给程序
优先接入：
- 计算器/代码执行器
- SQL/API 查询
- 搜索
- 日历/CRM/工单系统
- 规则引擎
- 文档解析器

原则：**确定性计算不要交给 LLM 心算；实时数据不要靠模型记忆。**  
这通常比换更大模型更有效。

## 6. 路由：让小模型做简单事，大模型做难题
用分类器/小模型/规则先判断任务难度：
- 简单：小模型 + 模板
- 中等：小模型 + RAG
- 困难/高风险：大模型 + 多候选 + 验证器
- 不确定：升级人工或大模型

可显著降低成本，同时把预算集中到困难样本。路由依据可用：问题长度、检索置信度、输出置信度、格式校验结果、历史失败类型。

## 7. 缓存与复用
- **精确缓存**：相同输入直接返回。
- **语义缓存**：相似问题复用答案，需阈值和失效策略。
- **检索缓存**：热门查询缓存检索结果。
- **提示前缀缓存**：复用长系统提示和文档前缀。
- **工具结果缓存**：API/SQL 查询缓存。

客服、FAQ、代码助手场景收益很大。

## 8. 组合式最小可行方案
对大多数业务，先上这个 stack：

```text
用户问题
→ 任务分类/路由
→ 查询改写
→ 混合检索 + rerank
→ 结构化提示 + 动态 few-shot
→ LLM 生成 JSON
→ 规则/小模型校验
→ 失败则检索补充/重试/升级大模型
→ 引用证据输出
→ 缓存结果
```

通常能带来：幻觉下降、格式合规上升、人工返工减少、长尾任务通过率提升。是否“大幅”取决于任务，但这是低成本最高概率路径。

## 9. 成本控制策略
- 只对高不确定样本做 self-consistency / best-of-N；
- 用规则和小模型做第一道验证；
- 用 reranker 减少喂入 token；
- 用语义缓存；
- 失败重试限制 1～2 次；
- 长文档先摘要/检索，不整篇塞入；
- 用便宜模型做改写、分类、抽取、校验，大模型只做最终难例。

## 10. 推荐实施顺序
1. 建评测集和失败分类；
2. 上结构化输出、动态 few-shot、上下文压缩；
3. 上 RAG：混合检索 + rerank + 引用；
4. 上规则/小模型验证器；
5. 对高不确定样本加 self-consistency 或 best-of-N；
6. 上路由和缓存；
7. 每周根据失败样本迭代检索库、示例库、校验规则。

## 关键提醒
- **不要迷信复杂 multi-agent**：多数场景不如“检索 + 验证 + 路由”稳。
- **提示词不是数据库**：事实性问题必须外挂知识。
- **验证器比生成器更重要**：低成本提升往往来自“能发现并纠正错误”。
- **必须做 A/B 测试**：采样温度、候选数、rerank 数量都要按任务调。
- **高风险场景保留人工兜底**：医疗、法律、金融、生产变更等不要让模型自动决策。

一句话总结：**不训练模型时，最大提升来自“外部知识 + 工具 + 验证闭环 + 自适应推理预算 + 路由缓存”，而不是单纯换更长的提示词。**

## 回答 B

【方案：低成本、不额外训练，提升现有 LLM 性能】

先说结论：不改模型权重、不做额外训练，也能通过“系统层优化”在具体任务上显著提升效果。关键是不要只改提示词，而是把 **提示、检索、工具、验证、路由、缓存、评测** 组合成流水线。通用能力没有免费午餐，但面向明确任务，通常可获得明显收益。

### 1. 最高性价比的 7 个抓手

1. **任务契约与结构化输出**  
   明确角色、目标、输入、约束、验收标准、输出格式。强制 JSON/表格/字段，减少跑题和不可用输出。  
   做法：系统提示 + 输出 schema + 示例 + 失败重试。

2. **动态少样本与提示链**  
   不要固定长提示。按问题类型检索最相似的高质量示例，放入 2—5 个；把复杂任务拆成“理解—计划—执行—检查”多步提示。

3. **混合 RAG：检索增强 + 引用核验**  
   用 BM25 + 向量检索混合召回，查询改写，重排，元数据/权限/时效过滤，父子分块。回答必须给引用来源，并做引用一致性检查。对知识问答、客服、文档分析提升很大。

4. **工具调用：计算器、代码、SQL、搜索、业务 API**  
   数学、统计、表格、日期、代码任务不要只让模型“想”，让它调用工具执行。采用“计划—调用—观察—修正”的 ReAct 式流程。

5. **自洽投票 + 验证器 + 反思修正**  
   对高价值问题采样 3—5 个答案，做多数投票或 best-of-N；用规则、单元测试、LLM 评审器、引用核验筛掉坏答案。失败后把错误反馈给模型重试一次。

6. **小模型/大模型路由与级联**  
   简单问题走小模型或缓存；难问题、低置信问题升级大模型；高风险问题加人工复核。可按意图、难度、风险、成本做路由，而不是全部用大模型。

7. **语义缓存与评测闭环**  
   常见问题做精确缓存和语义缓存；记录日志、失败案例、成本、延迟；建立 30—100 条代表性评测集，每周回放失败案例，迭代提示和检索。

### 2. 最小可行流水线

一个低成本通用流水线可以这样搭：

**意图识别 → 查询改写 → 混合检索 → 重排过滤 → 上下文压缩 → 结构化提示 → LLM 生成 → 规则/LLM 验证 → 引用核验 → 低置信澄清或升级 → 缓存 → 日志回放**

高价值问题再叠加：**3—5 次采样自洽 + best-of-N + 验证器 + 失败重试**。  
低风险问题走：**小模型 + 缓存 + 简短提示**。

### 3. 按任务选配

- **知识问答/文档分析**：混合 RAG + 重排 + 引用核验 + 多跳检索。  
- **客服/业务办理**：意图识别 + 槽位填充 + 知识库 + 规则引擎 + 人工兜底。  
- **代码任务**：代码执行 + 单元测试 + 多候选生成 + 失败修复循环。  
- **数学/数据分析**：代码执行 + 计算器 + 数值校验 + 表格解析。  
- **高风险场景**：双模型评审 + 规则校验 + 安全护栏 + 人工审核。  
- **长文档**：语义分块 + 摘要压缩 + 滑窗 + 关键信息筛选。

### 4. 成本控制

优先做：语义缓存、前缀缓存、小大模型路由、批处理、限制自洽次数、只对高价值请求做多候选、低置信转人工、异步处理。  
不要盲目对所有请求都上复杂多智能体；先按收益/成本分级。

### 5. 评估指标

建议同时看：任务准确率、事实一致率、引用覆盖率、幻觉率、任务完成率、人工接管率、单请求成本、P95 延迟。  
上线前做 A/B 对照；每次只改一个模块，避免“感觉变好但无法归因”。

### 6. 推荐实施顺序

**P0（1—2 周）**：结构化提示 + 动态示例 + 评测集 + 日志。  
**P1（2—4 周）**：混合 RAG + 引用核验 + 工具调用 + 规则验证。  
**P2（1—2 月）**：自洽投票 + 验证器 + 小大路由 + 语义缓存 + 失败回放。  

一句话：**不改模型，改“模型外面的系统”**。最有效的组合通常是：**结构化提示 + 混合检索 + 工具执行 + 验证器 + 路由缓存 + 评测闭环**。
