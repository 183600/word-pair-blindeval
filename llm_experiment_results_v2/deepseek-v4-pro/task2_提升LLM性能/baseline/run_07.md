# [v2:deepseek-v4-pro] 任务2 提升LLM性能 | 条件: baseline | 第 7 次

**Prompt:** 怎么低成本不需要额外训练大幅提升现有LLM的性能

**耗时:** 99.0s | tokens: 94/6413

---

可以在**不训练模型权重**的前提下，通过“推理时优化”明显提升现有 LLM 的任务表现。下面按成本/收益从高到低列，很多方法可以叠加使用。

---

## 一、提示与上下文工程：几乎零成本，先做

### 1. 强化系统提示
把模型角色、任务目标、约束、输出格式、判断标准写清楚。  
示例：

```text
你是资深财务合规审核员。根据《XX报销制度》判断报销是否合规。
要求：
1. 逐条对照制度，不臆造制度外规则；
2. 只输出 JSON：{"allowed": true/false, "reasons": ["..."], "risk": "低/中/高"}
```

### 2. 让模型分步思考
对于数学、逻辑、代码调试、复杂分析任务，添加：

```text
请一步一步思考，先分析问题，再给出最终答案。
```

这比直接要答案稳定很多。

### 3. 给高质量 few-shot 示例
提供 3~5 个“输入 → 推理过程 → 输出”的示例。  
注意：
- 示例要覆盖边界情况；
- 标签要均衡；
- 格式必须和期望输出一致。

### 4. 输出格式约束
要求 JSON、Markdown 表格、固定字段，能减少解析失败，提升可用性。  
例如：

```text
只返回 JSON，不要输出解释。
```

如果 API 支持 JSON mode / function calling，优先用。

### 5. 上下文选择与排序
不要把长文档全部塞进去。  
- 先用检索或摘要选最相关片段；
- 关键信息放在开头或结尾，避免“lost in the middle”；
- 对长文可以让模型先摘录相关原文，再回答。

### 6. 自动提示优化
可以用 DSPy、APO 等框架自动搜索更好的提示词和 few-shot 示例。本质是调用模型迭代，不训练模型权重，但需要一定调用成本。

## 二、解码与采样策略：提升准确率，但成本略增

### 1. 自我一致性
对数学、逻辑、分类等有明确答案的任务：

- 温度调到 0.5~0.8；
- 采样 5~10 次；
- 对答案做多数投票。

通常能明显提升推理题准确率，但成本变为 N 倍。

### 2. Best-of-N
生成多个候选答案，再用另一个 LLM 或规则打分，选最优。  
适合开放生成、翻译、摘要等没有唯一标准答案的任务。

### 3. 调温度与 top-p
- 分类、抽取、信息检索：温度 0~0.2；
- 推理：0.3~0.7；
- 创意写作：0.7~1.0。

### 4. 约束解码
使用 JSON Schema、正则、语法约束，保证输出合法。  
工具如 OpenAI JSON mode、vLLM guided decoding、outlines、guidance 等。

### 5. 低置信度触发复核
如果 API 返回 logprobs，可以对关键答案看概率。  
低置信度时：
- 转给更强模型；
- 或转人工复核。

## 三、外部知识与工具：补齐模型短板

### 1. RAG：检索增强生成
很多“性能差”其实是知识缺失或过时。RAG 不需要训练，成本低。

做法：
- 把知识库切块、嵌入、建向量库；
- 用户问题先检索 top-k 片段；
- 把片段塞进 prompt，并要求引用来源。

提升技巧：
- 问题改写：先让 LLM 改写/扩展问题再检索；
- HyDE：先让 LLM 生成一个假设答案，再用它检索；
- 重排模型：如 bge-reranker、Cohere Rerank，能提高检索质量；
- 要求模型“仅根据给定资料回答，并标注来源”，减少幻觉。

### 2. 工具调用 / Function Calling
让模型调用外部工具，而不是自己硬算。适合：
- 算术计算；
- 实时搜索；
- 数据库查询；
- 代码执行；
- 调用内部 API。

例如让它输出：

```json
{"tool": "calculator", "input": "123456 * 0.13"}
```

这能大幅减少数值错误和事实幻觉。

## 四、多模型协作与工作流

### 1. 模型路由
简单任务用小模型，复杂任务用大模型。  
不用训练路由器，可以用：
- 关键词规则；
- 文本长度；
- 小模型先分类；
- 置信度阈值。

这样在总成本不变的情况下，整体性能更高。

### 2. 多模型投票
同一模型多次采样，或者不同模型结果投票。  
适合分类、选择、事实判断等任务。

### 3. 自我反思与修正
让模型先生成初稿，再自我检查：

```text
请检查你的答案是否存在以下问题：
1. 事实错误；
2. 计算错误；
3. 没有满足用户约束；
4. 格式不符合要求。
如果有问题，请修正后重新输出。
```

也可以用另一个模型充当“批评者”，检查后修改。  
对质量要求高的任务，这种“生成—检查—修正”循环提升明显。

### 4. 多智能体分工
例如：
- 规划者：拆解任务；
- 执行者：分步执行；
- 审核者：检查结果。

适合复杂项目、报告生成、代码开发等，但复杂度和调用成本较高。

## 五、工程优化：降本提效，间接支持更多采样

这些不直接提升准确率，但能省出预算来跑更多采样、投票、反思。

### 1. 缓存
- 精确缓存：相同问题直接返回历史答案；
- 语义缓存：相似问题用向量检索，相似度高于阈值直接复用。

### 2. 提示缓存
很多 API 支持前缀缓存。把固定系统提示、few-shot 放前面，减少重复计费。

### 3. 批处理与并发
合并请求、异步调用，提高吞吐，降低延迟。

### 4. 推理引擎与量化
使用 vLLM、SGLang、TensorRT-LLM、llama.cpp 等，配合 FP8/INT8 量化。  
质量损失通常很小，但推理成本大幅下降。

---

## 六、推荐落地顺序

1. 明确任务指标：准确率、格式合规率、事实一致性等。
2. 建 50~100 条测试集，覆盖常见和困难 case。
3. 跑当前基线。
4. 先加：系统提示、few-shot、CoT、结构化输出。
5. 对知识密集/时效任务加：RAG、工具调用。
6. 对高价值任务加：自我一致性、多模型投票、反思修正。
7. 用缓存、路由优化成本。

---

## 注意点

- 不存在对所有任务都翻倍的银弹，但组合使用通常能显著提升。
- CoT、多采样、反思会增加延迟和成本，需要和预算平衡。
- 提示工程可能过拟合小测试集，要用独立测试集验证。
- 如果任务强依赖实时知识、精确计算，RAG 和工具调用通常比改提示更有效。
