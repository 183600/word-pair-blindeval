## 回答 A

**怎么低成本、不需要额外训练，大幅提升现有 LLM 的性能？**

核心思路是：**不改变模型权重，只优化提示、推理路径、上下文、检索、解码和系统编排。**

## 1. 推理增强：让模型“想清楚再说”

这是提升准确率最明显、成本最低的一类方法。

### 零样本思维链
在问题末尾加一句：

> 请一步一步思考，先给出推理过程，再给出最终结论。

很多任务会立刻提升表现，尤其是数学、逻辑、多步骤决策。

### 少样本思维链
给 2—5 个带完整推理过程的示例。示例要覆盖关键步骤，不要只给最终答案。

### 自一致性
让模型用较高温度生成 5—9 个候选回答，然后投票或综合。  
适合选择题、判断题、分类、推理题。

### 多方案比较
让模型先给出 2—3 个候选方案，再比较优劣，最后选最优。  
这会减少“一条路走到黑”的错误。

## 2. 提示工程：把提示写得更像“工程文档”

### 五要素提示法
每次提示尽量包含：

1. 角色  
2. 任务  
3. 上下文  
4. 输出格式  
5. 禁止事项

示例：

> 你是资深数据分析师。  
> 任务：分析下面销售数据，找出异常点。  
> 上下文：数据如下……  
> 输出格式：用表格列出异常点、可能原因、建议动作。  
> 禁止：不要编造数据；不要输出无关内容。

### 输出格式约束
让模型输出 JSON、Markdown 表格、列表、代码块。  
结构化输出能减少解析错误，也更容易被下游程序使用。

### 任务分解
不要一次让模型完成太复杂的事。  
把大任务拆成流水线：

> 第一步：提取关键信息  
> 第二步：分类问题类型  
> 第三步：生成答案  
> 第四步：检查答案

每一步单独调用模型，整体质量通常更高。

## 3. 检索增强生成：给模型“外部记忆”

不训练模型，但给它查资料的能力。

- 把文档切块，向量化，存入向量库。  
- 用户提问后，检索最相关的 3—10 个片段。  
- 把这些片段放进 prompt，让模型基于证据回答。  
- 要求模型引用来源。

这能显著降低幻觉，提升事实型和知识型任务性能。

## 4. 上下文工程：管理好模型“眼前的信息”

模型对上下文的位置很敏感。

- 重要信息放前面。  
- 指令要明确，不要淹没在长文档里。  
- 对话历史过长时，先做摘要压缩。  
- 删除重复、无关、冲突的信息。  
- 使用标题、编号、分隔符，减少歧义。

## 5. 解码策略优化：用采样换取质量

不训练，只调参数和采样方式。

### 温度
- 事实、推理、数学任务：`temperature = 0.0—0.3`  
- 创意、写作、头脑风暴：`temperature = 0.7—0.9`

### top_p
一般 `0.8—0.95`，配合温度调整。

### best-of-n
生成多个候选，再选最优。  
可以用规则打分、代码验证、人工投票，或者让模型自评。

### 约束解码
限制模型只能输出合法 token，例如 JSON 语法、SQL 语法、指定标签。  
能减少格式错误。

## 6. 系统级编排：多模型、多角色、多工具

### 模型路由
简单任务用便宜小模型，复杂任务用大模型。  
例如：

- 小模型：分类、抽取、改写、意图识别  
- 大模型：复杂推理、长文生成、多步决策

### 多角色协作
用同一个模型或多个模型扮演不同角色：

> 生成者：写出初稿  
> 批评者：找出问题、漏洞、错误  
> 修订者：根据批评修改

循环 1—2 轮，质量提升明显。

### 工具调用
不要让模型硬算。  
让模型调用：

- 计算器  
- 代码解释器  
- 搜索引擎  
- 数据库查询  
- 日历、邮件等外部 API

这相当于给模型“手脚”。

## 7. 最低成本组合建议

如果只做几件事，我推荐这个组合：

1. **零样本思维链**：所有复杂任务都加一句“请一步一步推理”。  
2. **自一致性**：重要任务采样 5 次，投票或综合。  
3. **结构化提示模板**：角色、任务、格式、禁止项写清楚。  
4. **RAG**：事实型、知识型任务接外部检索。  
5. **best-of-n**：生成多个候选再选最优。

这五项基本不需要额外训练，也不需要很高算力，但对很多任务能带来显著提升。

一个通用模板：

```text
你是【领域】专家。
任务：{一句话描述目标}
上下文：
<<<
{相关文档或背景}
>>>
要求：
1. 先分析关键信息和约束；
2. 给出 2—3 个候选方案并比较；
3. 选择最优方案并说明理由；
4. 最终输出 JSON：
{"answer": "...", "reason": "...", "confidence": 0.0}
```

这套方法的核心是：**把模型性能从“训练权重”转移到“提示、检索、推理路径和系统设计”上。**

## 回答 B

可以，不微调模型也能明显提升现有 LLM 的表现。核心思路是：**推理时增强 + 外部能力扩展 + 更好的解码策略**。下面按“成本从低到高、见效从快到慢”整理。

---

## 一、零成本：提示工程和上下文学习

这些方法只改 prompt，不花额外训练成本，但效果往往很显著。

### 1. 明确角色、目标和约束
不要让模型猜你要什么。

差的提示：
> 帮我写个方案

更好的提示：
> 你是一名资深 B2B SaaS 产品经理。请为一个面向中型企业的数据分析平台写一份上线发布方案。要求：  
> - 结构包含背景、目标、关键动作、时间表、风险  
> - 语言简洁，不超过 800 字  
> - 用 Markdown 输出

### 2. 给 Few-shot 示例
给 2~5 个高质量示例，能大幅提升分类、抽取、结构化输出、风格模仿等任务效果。

示例：
> 输入：这个手机续航太差了  
> 输出：{"sentiment": "negative", "aspect": "battery"}  
>   
> 输入：屏幕很清楚，但有点贵  
> 输出：{"sentiment": "mixed", "aspect": "screen,price"}  
>   
> 现在输入：物流很快，包装也很好

示例要贴近任务、格式一致。用检索选择相似示例效果更好，这就是“动态 few-shot”。

### 3. 思维链 Chain-of-Thought，CoT
对推理、数学、逻辑、复杂决策类任务，让模型“先想后答”。

可以简单加一句：
> 请一步一步思考，先分析再给出最终答案。

更稳定的是要求它输出推理过程：
> 先列出已知条件，再列出求解步骤，最后给出答案。

零样本 CoT 在很多推理任务上能带来几个点到十几个点的提升。

### 4. 结构化输出约束
让模型输出 JSON、XML、Markdown，或者指定字段，能减少解析失败、提高可用性。

例如：
> 请只输出 JSON，不要输出其他内容。格式如下：  
> {"summary": "...", "keywords": ["..."]}

### 5. 任务分解
复杂任务不要让模型一次完成。

可以这样设计：
> 请先制定一个计划，列出步骤。  
> 然后逐步执行，每步给出结果。  
> 最后汇总成最终答案。

这比直接让它写长篇内容质量更高。

## 二、低成本：采样与解码策略

这些方法会增加一些推理成本，但不需要训练。

### 1. 调整 temperature 和 top_p
- 精确任务，例如分类、抽取、数学、代码：用 `temperature=0` 或接近 0，贪婪解码。
- 创意任务，例如写作、头脑风暴：可以用 `temperature=0.7~0.9`，但配合多候选。

很多人在 API 里默认用高 temperature，导致精确任务不稳定。调低 temperature 是最便宜的提升。

### 2. Self-Consistency，自洽性
对推理类任务特别有效：

1. 让模型用 CoT 生成 5~10 条推理路径；
2. 对最终答案进行多数投票。

例如数学题，单次 CoT 正确率可能 70%，self-consistency 可以提升到 80%+。代价是多次采样，token 成本增加，但不需要训练。

### 3. Best-of-n 采样
生成多个候选答案，然后用规则、打分模型或人工选择最佳。

如果任务有明确评价标准，例如代码是否能运行、答案是否符合格式，可以自动筛选。

### 4. 多模型集成或辩论
用两个模型互相评审：
- 模型 A 生成答案；
- 模型 B 批评/打分；
- 让模型 A 根据反馈修改。

即使只有一个模型，也可以让它自己“扮演批评者”来改进。

## 三、无训练扩展：RAG 与工具调用

如果任务需要外部知识、实时信息、精确计算，LLM 本身可能不够。这时可以通过外部模块扩展能力。

### 1. RAG，检索增强生成
适用：知识问答、企业文档、专业领域、实时信息。

做法：
1. 把文档切块，向量化，存入向量库；
2. 用户提问时检索 top-k 相关片段；
3. 把片段拼进 prompt，并要求模型只根据资料回答。

示例 prompt：
> 请根据以下资料回答问题。如果资料中没有答案，请说“资料中未提及”。  
> 资料：  
> ...  
> 问题：...

RAG 能显著降低幻觉，提升知识密集型任务表现。构建成本低，不需要训练。

### 2. 工具调用 / Function Calling
让模型调用外部工具，弥补计算、搜索、代码执行等短板。

常用工具：
- 计算器：精确数学计算；
- 搜索引擎 / API：实时信息；
- 代码解释器：执行代码、处理数据；
- 数据库 / SQL：查询结构化数据。

例如让模型做复杂日期计算，不如让它调用 Python 函数。

### 3. ReAct / Agent 模式
让模型按照“思考 → 行动 → 观察 → 再思考”循环工作。

示例：
> 你可以使用以下工具：  
> - search(query)：搜索互联网  
> - calculator(expression)：计算数学表达式  
>   
> 请先思考下一步该做什么，然后调用工具，观察结果，继续推理，直到给出最终答案。

这种模式对多步问题、信息检索、数据分析非常有效。

## 四、自我改进与多智能体工作流

不需要训练，但可以通过多轮推理提升质量。

### 1. Self-Refine
让模型生成答案后，再让它自己批评并修改。

分三步：
1. 生成初稿；
2. 让它列出初稿的问题；
3. 根据问题重写。

例如：
> 请指出上面答案中的错误、遗漏和逻辑不通之处，然后给出改进后的版本。

### 2. 验证器过滤
如果任务有可自动验证的标准，可以生成多个候选，再自动筛选：
- 代码：运行测试用例；
- 数学：用计算器验证；
- 事实：用检索结果核对。

### 3. 多智能体协作
一个模型负责生成，一个模型负责批评，一个模型负责修改。可以用同一模型扮演不同角色，也可以混合不同模型。

## 五、系统层优化：降低推理成本和延迟

这些方法主要提升“性能/成本”比，让同等成本下能跑更多推理。

### 1. 量化与推理加速
- 使用 AWQ、GPTQ、GGUF 等量化方案；
- 使用 vLLM、TensorRT-LLM、llama.cpp 等推理框架；
- 开启 FlashAttention。

这不会降低输出质量太多，但能大幅降低显存占用和推理成本。

### 2. 推测解码 Speculative Decoding
用小模型快速生成候选 token，由大模型验证。可以保持大模型输出质量，同时加速 2~3 倍。

### 3. KV Cache 前缀缓存
如果大量请求共享相同前缀，例如相同的 system prompt 或 RAG 文档，可以缓存 KV cache，减少重复计算。

### 4. 批处理与连续批处理
提高吞吐，降低单位 token 成本。尤其适合离线批量任务。

## 六、实践配方：不同任务怎么组合

| 任务类型 | 推荐组合 |
|---------|---------|
| 推理/数学 | CoT + Self-Consistency + 计算器工具 |
| 知识问答 | RAG + 引用要求 + 低 temperature |
| 代码生成 | 多候选 + 运行测试 + Self-Refine |
| 分类/抽取 | Few-shot + 结构化输出 + 低 temperature |
| 写作/创意 | 大纲-草稿-自我批评 + 多候选重排 |
| 长文档分析 | 任务分解 + 分段处理 + 汇总 |

---

## 注意事项

1. **这些方法不能给模型增加它原本没有的知识**。如果模型本身能力很弱，提升有限。
2. **多次采样会增加 token 成本**，建议只在关键任务上使用 self-consistency 或 best-of-n。
3. **提示过长会稀释注意力**。保留关键信息，去掉噪音。
4. **如果任务需要大量新领域知识或风格**，最终可能仍需要微调或换更强模型。但在此之前，先试这些方法，通常能低成本拿到明显提升。

最推荐先试的三招：  
- 低 temperature + 清晰结构化提示  
- CoT + Self-Consistency  
- RAG / 工具调用  

这三类组合起来，在很多场景下能带来“看起来像换了个更强模型”的提升。
