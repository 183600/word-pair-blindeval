## 回答 A

可以提炼出几个关键灵感：**路由/调度、缓存/复用、投票/集成、分解/重组、检索/工具、验证/过滤、结构化/约束、搜索/剪枝**。  
不训练、低成本地大幅提升现有 LLM 性能，主要靠**推理时策略、提示工程、检索增强、工具使用和系统层优化**。

## 一、推理时采样与集成

1. **自一致性投票**  
   同一个问题用较高温度采样 5—10 次，得到多个候选答案，然后投票或让模型自己汇总。对数学、代码、逻辑推理类任务提升明显。

2. **多提示集成**  
   用不同提示角度生成多个答案：  
   - 换角色：专家、教师、工程师  
   - 换格式：先给结论、先给步骤、先给表格  
   再让模型综合多个答案，通常比单次回答更稳定。

3. **验证器/批评器**  
   先让模型作答，再让它自己批评、找错误、修正。  
   如果有代码、数学题，可以用代码执行、单元测试、规则检查来验证候选答案，过滤掉错误结果。

## 二、提示与上下文工程

4. **动态少样本**  
   从已有数据、日志或知识库中检索与当前问题最相似的示例，放进提示里。比手写固定示例更有效。

5. **思维链**  
   复杂任务加一句“让我们一步一步思考”，或提供带推理步骤的少样本示例。  
   更强的做法是：  
   - 先制定计划  
   - 再逐步执行  
   - 最后检查结果  

6. **任务分解**  
   把大任务拆成子任务，逐个解决。例如：  
   写报告 → 先列大纲 → 再逐段生成 → 再统一检查。

7. **上下文压缩与排序**  
   把最重要的信息放在开头和结尾，中间放次要信息。  
   长文档先摘要、提取关键词、分段检索，减少上下文噪声。

8. **结构化输出**  
   要求输出 JSON、表格、Markdown，并给出 Schema 和示例。  
   结构化的输出更容易解析、校验和复用，也能减少模型胡言乱语。

## 三、检索增强与工具使用

9. **RAG 检索增强**  
   外接向量库、搜索引擎、知识库，把检索到的相关资料放进上下文。  
   这能明显减少幻觉，提升知识密集型任务效果。

10. **工具调用**  
    让模型使用计算器、代码执行器、API、数据库、表格工具。  
    原则是：**让模型负责推理和生成，让工具负责精确计算和事实查询**。

11. **外部记忆**  
    长对话或长任务中，用外部存储保存摘要、实体、状态。  
    即使超出上下文窗口，也能继续工作。

## 四、推理时搜索与规划

12. **思维树/图搜索**  
    让模型生成多个下一步，分别评分，只扩展最优分支。  
    适合复杂规划、创意发散、多步推理。

13. **反思与修订**  
    生成初稿后，让模型根据约束条件自我批评并修改。  
    例如：“请检查以上回答是否满足以下要求，不满足则修改。”

14. **约束解码**  
    用正则、语法或 JSON Schema 限制输出，减少无效生成，提高可用率。

## 五、系统层优化

15. **语义缓存**  
    相似问题直接复用之前的答案，降低延迟和成本。  
    可以用嵌入相似度做缓存判断。

16. **模型路由**  
    简单任务用小模型，复杂任务路由到大模型。  
    既能保证质量，又能大幅降低成本。

17. **并行采样与异步调用**  
    同时生成多个候选答案，再筛选合并，提高吞吐和最终质量。

18. **推理加速**  
    使用 vLLM、TensorRT、量化到 FP8/INT8 等方法，不改变模型权重，但能提高生成速度、降低单次成本。

## 推荐组合打法

一个比较稳的低成本组合是：

> **路由 → 检索 → 动态少样本 + 思维链 → 多次采样 + 验证器 → 结构化输出**

例如：

1. 先判断任务难度，简单任务用小模型；  
2. 知识类问题先检索外部知识；  
3. 用相似示例 + 思维链提示；  
4. 采样 5 次，投票或用规则验证；  
5. 最后输出 JSON/表格，便于后续解析。

这套方法不需要训练模型，但能在推理、知识密集型、代码、数学、结构化输出等场景显著提升效果。

## 回答 B

不需要额外训练、低成本地提升现有 LLM 的性能，核心思路有两类：

1. **提升单次调用质量**：通过推理时策略、提示工程、外部知识/工具，让模型“更聪明地思考”。
2. **提升系统整体效率/性价比**：通过缓存、量化、路由、投机解码等手段，在不改变模型权重的情况下降低延迟与成本。

下面按优先级和实操性整理成一套可直接落地的方案。

---

## 一、推理时策略：让模型“多想一想”

这类方法完全不改权重，只改变采样/解码/交互方式，对数学、逻辑、代码等任务提升非常明显。

### 1. 思维链（Chain-of-Thought, CoT）
最简单有效的方法。在提示中要求模型分步骤推理。

**做法：**
- 加上：“请一步步思考，先列出已知条件，再推导，最后给出答案。”
- 对复杂问题，可要求：“先分析问题类型，再给出解题步骤。”

**适用：** 数学、逻辑推理、规划、代码调试。

### 2. 自洽性采样（Self-Consistency）
让模型独立生成多个答案，然后投票或取多数结果。

**做法：**
- 同一问题采样 5–10 次（temperature 设 0.7 左右）。
- 对所有答案进行聚类/投票，选择出现频率最高的答案。

**适用：** 数学、常识推理、选择题、分类任务。  
**成本：** 增加 N 倍推理量，但可显著提升准确率。

### 3. Best-of-N 采样
类似 Self-Consistency，但用奖励模型/规则打分选最优，而不是投票。

**做法：**
- 采样 N 个候选，用规则（如代码能否运行、格式是否正确）或另一个 LLM 打分。
- 选择得分最高的输出。

**适用：** 代码生成、创意写作、翻译等有明确评价标准的任务。

### 4. 反思与自我修正（Self-Refine / Reflexion）
让模型先给出答案，然后自己检查、批评并改进。

**做法：**
- 第一轮：生成答案。
- 第二轮：提示“请检查上面的答案是否存在错误或遗漏，并给出改进版。”
- 可重复 2–3 轮，直到输出稳定。

**适用：** 代码生成、数学证明、复杂问答。

### 5. 思维树/思维图（Tree/Graph of Thoughts）
将问题拆成多步，每步生成多个候选，再搜索最优路径。

**做法：**
- 使用 LangGraph、LangChain 等框架实现。
- 每一步生成 2–4 个候选，用 LLM 评分，保留高分分支继续扩展。

**适用：** 需要规划、搜索、多步推理的任务，如 24 点游戏、旅行规划、复杂决策。

### 6. 多智能体辩论/协作
用同一模型扮演不同角色（如正方、反方、裁判），相互质疑后收敛答案。

**做法：**
- 让模型生成两个相反观点。
- 再让模型评判哪个观点更合理，并综合出最终答案。

**适用：** 开放性问答、政策分析、创意评估。

## 二、提示与上下文工程：几乎零成本的优化

### 1. Few-shot 示例精选
给模型 2–5 个高质量示例，示例格式要与目标输出完全一致。

**技巧：**
- 示例要覆盖边界情况。
- 示例答案要简洁、准确，避免错误示范。
- 如果输出格式复杂，示例比指令更有效。

### 2. 系统提示词设计
明确角色、任务、约束、输出格式。

**模板：**
```
你是一名资深软件工程师。
任务：将以下需求转化为 Python 函数。
要求：
- 只输出代码，不要解释。
- 函数名和参数名使用 snake_case。
- 包含必要的类型注解。
```

### 3. 结构化输出约束
要求模型输出 JSON、XML 或 Markdown 表格，减少后处理成本。

**做法：**
- 在提示中给出 JSON Schema 示例。
- 使用 OpenAI Function Calling、JSON mode 或正则约束解码。

### 4. 上下文压缩与记忆管理
长对话或长文档会稀释注意力，导致性能下降。

**做法：**
- 定期总结历史对话，只保留关键信息。
- 使用 LangChain 的 `ConversationSummaryMemory` 或 `ConversationBufferWindowMemory`。
- 对长文档先分段检索，再拼接相关片段。

### 5. 自动提示优化（DSPy 等）
用少量标注数据自动搜索最优提示词，无需训练模型。

**工具：**
- DSPy：自动优化提示结构、few-shot 示例。
- PromptBench、PromptPerfect 等。

## 三、外部知识与工具：扩展模型能力边界

### 1. 检索增强生成（RAG）
将外部知识库接入 LLM，回答时先检索相关内容再生成。

**做法：**
- 使用向量数据库（Chroma、FAISS、Milvus）存储文档。
- 查询时检索 top-k 片段，拼接到提示中。
- 可加入引用来源，提升可信度。

**适用：** 企业知识库、产品文档、法律/医学等垂直领域。

### 2. 工具/API 调用
让模型使用计算器、搜索引擎、代码解释器等工具。

**做法：**
- 使用 OpenAI Function Calling、LangChain Tools 或 ReAct 模式。
- 定义工具：搜索、计算、数据库查询、代码执行。
- 模型生成工具调用指令，系统执行后返回结果。

**适用：** 实时信息、精确计算、代码运行、数据查询。

### 3. 代码解释器
对于需要精确计算或数据处理的场景，让模型生成 Python 代码并执行。

**做法：**
- 使用 ChatGPT Code Interpreter 或本地 E2B、Jupyter 内核。
- 将模型生成的代码在沙盒中运行，返回结果。

## 四、系统架构层：提升效率与性价比

这类方法不提升单次答案质量，但能大幅降低延迟和成本，让高成本策略（如 Self-Consistency）变得可行。

### 1. 模型路由/级联
小模型处理简单请求，大模型处理复杂请求。

**做法：**
- 用规则或轻量分类器判断难度。
- 简单任务调用 7B 模型，复杂任务调用 70B 模型。
- 可结合置信度：小模型不确定时升级到大模型。

**成本节省：** 50%–80%。

### 2. 语义缓存
对相似请求直接返回缓存结果，避免重复推理。

**工具：**
- Redis + 向量相似度（如 RedisVL、GPTCache）。
- 设置相似度阈值（如 0.95），命中则返回缓存。

**适用：** 客服、常见问题、高频 API 调用。

### 3. 提示缓存（Prompt Caching）
缓存系统提示或固定前缀的 KV Cache，减少重复计算。

**工具：**
- OpenAI 自动提示缓存（对长前缀免费）。
- vLLM、SGLang 支持 prefix caching。

**成本节省：** 长系统提示场景可节省 50% 以上。

### 4. 量化与推理加速
使用 AWQ、GPTQ、BitsAndBytes 等量化，或 vLLM、TensorRT-LLM、llama.cpp 等推理引擎。

**效果：**
- 4-bit 量化显存降低 4–6 倍，吞吐提升 2–3 倍。
- 对质量影响通常 < 1%。

### 5. 投机解码（Speculative Decoding）
用小模型生成候选 token，大模型并行验证，加速 2–3 倍。

**工具：**
- vLLM、SGLang、TensorRT-LLM 均支持。
- 使用同家族小模型作为 draft model。

### 6. 约束解码
限制输出必须符合正则表达式、JSON Schema 或语法。

**工具：**
- Outlines、LMQL、Guidance、SGLang。
- 保证格式正确，减少解析失败和重试。

## 五、按任务类型选择组合方案

| 任务类型 | 推荐组合 |
|---------|---------|
| 数学/逻辑推理 | CoT + Self-Consistency + Best-of-N |
| 代码生成 | CoT + 工具调用 + 约束解码 + Self-Refine |
| 知识问答 | RAG + 引用来源 + 思维链 |
| 开放式创意 | Best-of-N + 多模型投票 |
| 格式严格输出 | 结构化提示 + JSON mode + 约束解码 |
| 高并发服务 | 量化 + 缓存 + 模型路由 + 投机解码 |

---

## 六、注意事项

1. **没有银弹**：不同方法对不同任务效果差异大，需要小规模实验验证。
2. **成本与延迟权衡**：Self-Consistency、Best-of-N 会增加推理量，需配合缓存/量化控制成本。
3. **提示敏感**：同一策略在不同提示下效果可能波动，建议用 DSPy 等工具自动调优。
4. **评估先行**：建立轻量评估集，对比基线和方法组合的准确率、延迟、成本。

---

总结：**零训练提升 LLM 性能，优先用“推理时策略 + 提示工程 + RAG/工具”提升单次质量，再用“缓存 + 量化 + 路由 + 投机解码”降低系统成本**。大部分方法可以当天落地，且不需要任何权重更新。
