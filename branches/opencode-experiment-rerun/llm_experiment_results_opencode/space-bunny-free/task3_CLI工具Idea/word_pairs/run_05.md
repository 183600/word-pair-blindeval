# CLI工具 Idea：`suspect` —— 给"整个开发环境"做时间旅行二分

## 一句话

**`git bisect` 只二分代码。`suspect` 二分你的整个开发箱：Node 版本、lockfile、环境变量、全局包、系统时间、时区、DNS、磁盘、甚至"哪天开始坏的"。**

## 为什么独立开发者需要它

独立开发者最痛的场景不是"代码写错"，而是：

> "**上周三还好好的。今天突然 CI 挂了 / 构建挂了 / 测试莫名超时。我根本没改这块代码。**"

根因常常不在代码里：
- 某个 transitive dependency 昨天发了新版，lockfile 没锁住（**幽灵依赖 / 传递依赖 / 供应链**）
- Node 从 20悄悄升到 22（**环境漂移**）
- 某个 `.env`变量两周前被人删了（**变量失踪 / 配置漂移**）
- macOS 更新改了 DNS / 证书（**证书过期 / 边缘**）
- 甚至是**时区变了导致定时任务在午夜跑两次**

现在你只能手动 `git stash` 一路回退，或者删 `node_modules` 重装赌运气。`suspect` 把它变成**可自动化、可复现、可归档的"案情侦破"**。

## 核心概念

**Snapshots（快照）**：每次你提交代码或手动执行 `suspect save`，工具用一条命令把"世界状态"完整冻结：

```
code : HEAD sha + dirty diff (patch)
node      : nvm current + ~/.nvm/versions/node/*
lockfile  : package-lock.json / pnpm-lock.yaml / uv.lock / Cargo.lock
deps      : 全部已安装包的 name@version +完整 flat 清单（不只是顶层！）
env       : 变量名列表 + 值的哈希（不存明文，只存指纹）
system    : OS 版本、内核、CPU架构、locale、时区、磁盘剩余、CPU 限制
network : DNS 解析结果、代理设置、SSL 证书链指纹
global    : 全局包清单、PATH、CLI 工具版本
time      : 当前时刻（用于检测时区/时钟类 bug）
```

**Bisect（破案）**：跑测试用 `git bisect` 只能二分"提交序列"。`suspect bisect` 做的是**跨维度二分**：

```
suspect bisect "npm test" --from "3 days ago" --to HEAD
```

它按"信息增益最大"的维度排序做二分搜索（不只是线性回退提交），最后输出**最小致因集合**：

```
⚠️ 判定：第 2 号快照为拐点

  🔴 可疑变更（置信度 0.94）
     node      20.11.1 → 22.3.0
       ↳ 回归点：node@22 移除了 --experimental-fetch 下的默认 polyfill
     lockfile  3 个传递依赖被提升 ↳ tinyglobby0.2.9 → 0.2.11（上游 commit 破坏 exports 字段顺序）

  🟡 噪声（已排除）
     env 新增 STRIPE_KEY_TEST（值哈希变更，但测试不读取）
     global    无关     time/网络 无关

  💊 修复建议
     nvm use 20 && npm ci
     或：overrides 锁死 tinyglobby@0.2.9 📎 证据已归档：.suspect/case-2024-06-11/（含复现脚本 + 环境清单）
```

## 关键设计：三条"独立开发者友好"的取舍

1. **无 daemon、无云、无账号。** 所有数据留在 `.suspect/` 目录（可 `.gitignore`，也可选择加密提交进私有仓库）。这是隐私敏感开发者的最大买点。
2. **"快照只存差分"（content-addressed）**，和 git 同一个思路，所以 100 次快照的存储 ≈ 一次 `git gc`。
3. **判定失败 ≠ 白跑。** 二分中途只要出现"两次都不通过"的病态区间，工具会立刻停下来告诉你："这个 bug 不是单点导致的，是 flaky（抖动），建议去查 `retry` 那层" —— 给出**可执行的下一个动作**，而不是一个错误的结论。

## 最小可用版本（MVP，2 周可交付）

```
suspect init # 写 .suspect/config，声明"健康检查命令"
suspect save                 # 拍一张快照
suspect ls # 列出快照（像 git log，但显示的是"世界状态"）
suspect diff3f2a1b 7c9d0e   # 任意两快照的全维度差异suspect bisect "npm test" # 核心：破案
suspect report               # 把当前案子导成 Markdown /贴进 Issue
```

MVP 只需要支持 **Node/Python 两栈 + Git 代码维度**。先把80% 的场景（依赖漂移、node 版本、lockfile、env 变量）打穿。

## 差异化与扩展方向| 方向 | 说明 |
|---|---|
| **`suspect replay`** | 案子归档成可分享链接（自托管），同事点开就能在本地100% 复现那个坏掉的瞬间 |
| **`suspect ci`** | 在 GitHub Actions 里用，配 OCI 容器做"环境快照"（把 node/python/系统层也纳入二分） |
| **`suspect doctor`** | 常态巡检：扫描"幽灵依赖"（package.json 里写了但代码从未 import）、"失踪的 env 变量"、被弃用的 API |
| **`suspect watch`** | 后台每 15 分钟自动拍快照，一周后回答："这个 bug 上周就出现过，出现在你换掉 X 之后" |
| **付费点** | 团队共享快照仓库 / 时间线合并（像 git blame一样 blame你的环境）/ 私有 npm 镜像的"变更事件"接入 |

## 为什么值得做

- **需求真实且高频**：每个独立开发者的成长伴随"从能跑通到维护不动的系统"的转折点，这个痛点会在他撞到墙的那一刻变成刚需。
- **技术壁垒适中**：核心不是 AI，是**跨维度的状态捕获 + 自动化二分 + 病态区间检测**，这是一套确定性的、可测试的工程逻辑，做扎实了能长期受住。
- **天然可传播**：`suspect report` 生成的"案情报告"是一份漂亮、含信息量的 Markdown，天然是社交分享素材（"我居然被 Node 22 阴了"）。
- **一句话好记**：`git bisect` 查代码，`suspect` 查真相。
