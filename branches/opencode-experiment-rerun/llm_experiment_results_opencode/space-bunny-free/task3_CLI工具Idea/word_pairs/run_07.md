## 第二部分：从这些词长出来的 Idea

### 🔪 `prune` ——你的代码库体检刀> *"垃圾回收 / 园丁"* + *"依赖 / 债务"* + *"重构 / 考古"* + *"体检 / 化验单"* + *"X 光 / 片剂"* + *"杂草 / 剪刀"*

**slogan：给代码库拍一张 X 光，然后动手修剪。**

---

### 一、要解决的真实痛点

每个项目烂到一定程度，都会长出四种"暗伤"，但没人愿意花时间查：

| 症状 | 真实含义 | 造成的损失 |
|---|---|---|
| 👻 **幽灵依赖** `ghosts` | 代码里 `import lodash`，但 `package.json` 没声明 | 本地能跑、CI 挂、别人克隆下来就崩 |
| 🧟 **僵尸依赖** `zombies` | manifest 声明了 40 个包，代码里一个没用 | 安装慢 3 倍、攻击面扩大、审计噪音 |
| 🌿 **杂草** `duplicates` | 同一个包被传递引入 3 个版本 | 体积膨胀、行为诡异、`npm ls` 变成圣诞树 |
| 🦴 **化石** `archaeology` | 死代码、无引用导出、被删干净的旧逻辑 | 认知负担，改代码时误读 |

现有工具都只切其中一刀：`depcheck` 只管 JS 且只报未声明，`knip` 只管 JS/TS，`tsc --noUnusedLocals` 只管类型层，`import-linter` 只管架构约束，**没有一个把"体检 + 修剪"串成一条流水线的**。

### 二、核心命令设计

```bash
prune scan                  # 全量体检（默认动作）
prune ghosts                # 只查幽灵依赖
prune zombies               # 只查僵尸依赖
prune duplicates            # 只查版本分裂
prune orphans --env .env    # 查没人读的环境变量（暗袋里的机密）
prune archaeology src/old  # 考古：这个目录还有人引用吗？最后一次改动是谁？
prune fix --pr              # 自动生成"修剪"PRprune watch                 # 边写边提示
prune ci --format sarif     # CI 门禁，退出码非 0 阻断合并
```

### 三、差异化（为什么值得存在）

1. **一个工具五把刀**：体检维度统一，报告里给出"总体健康分"，而不是五个工具五份噪音报告。
2. **直接产出修复 PR**：这是关键——发现问题不解决问题等于没做。`prune fix` 自动删僵尸依赖、提声明、hoist 版本、开 PR，人只需要 review。
3. **零配置、零服务器、离线可用**：单二进制（Rust + tree-sitter），不上传任何代码，公司安全团队能放行；漏洞数据可选接 OSV。
4. **考古模式**：`prune archaeology` 结合 git 历史回答"这文件还有人用吗 / 谁引入的 / 删掉会影响谁"，这是 LLM 和 IDE 都答不好的问题。
5. **误报友好**：每个发现带置信度，支持 `// prune-ignore: reason` 行内注释豁免，`prune.toml` 声明组织级规则。

### 四、独立开发者为什么做得动

| 维度 | 评估 |
|---|---|
| **成本** | 几乎为零：无云服务、无 GPU、无数据库；1 台开发机 +域名 + npm/brew 分发 |
| **核心能力** | 静态分析 + tree-sitter + lockfile 解析 + git log，都是成熟技术，不需要前沿突破 |
| **差异化空间** | 现成工具都是「只诊断不修复」+「只管一门语言」，切入点清晰 |
| **增长** | 天然带传播：CI 失败时打印报告、PR 自动链接、原生 shell 补全 |
| **收入路径** | 开源核心 MIT；Pro 版（历史趋势库、monorepo 全局视图、策略基线、自定义规则、本地 LLM 解释）$9/月；团队版 $49/月 |

### 五、MVP 路线（10 周单兵版）

- **W1–2**：JS/TS + Python，只做 `ghosts` + `zombies`，彩色终端报告 + `--json`。目标：能替代 `depcheck`。
- **W3–4**：加 `duplicates`、GitHub Action、`--format sarif`、shell 补全。发布 v0.1（npm + brew）。
- **M3**：`fix --pr`（这才是护城河）、置信度评分、`prune.toml`。
- **M4**：Go / Rust 语言支持、`orphans`（环境变量 / 未引用配置）、`archaeology`。
- **M5**：官网、Pro 订阅、团队规则基线、Discord 社区。

### 六、衡量成功的三个数字

1. 周安装量（npm downloads）
2. 每周被扫描的仓库数
3. **每周自动生成的"修剪 PR"数量** —— 这是唯一说明用户真的信任它的指标

> 一句话总结：**别再做一个"告诉你哪里有问题"的工具，做一个"帮你把问题割掉"的工具。** 开发者不缺警告，他们缺的是敢按下的那把剪刀。
