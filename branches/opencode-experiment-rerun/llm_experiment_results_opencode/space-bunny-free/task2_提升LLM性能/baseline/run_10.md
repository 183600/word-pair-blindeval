# [rerun:space-bunny-free] 任务2 提升LLM性能 | 条件: baseline | 第 10 次

**Prompt:** 怎么低成本不需要额外训练大幅提升现有LLM的性能

**耗时:** 9.4s | **tokens:** 200/1518(推理 338) | **finish:** stop

---

## 核心思路：把"训练预算"换成"推理期算力 + 上下文预算"

不训练模型也能大幅提升效果，本质靠三件事：**更好的输入**（Prompt/上下文工程）、**更多的推理期计算**（采样、投票、分解）、**外部知识和工具**（RAG、工具调用、校验）。下面按"收益/成本比"排序。

---

## 一、Prompt / 上下文工程（几乎零成本，收益最大）

| 手段 | 做法 | 典型收益 |
|---|---|---|
| **结构化指令** | 角色 + 任务 + 约束 + 输出格式 + few-shot 示例，避免"含糊提问" | 10~40%（格式/风格类任务） |
| **思维链 CoT** | "先逐步推理再给结论" | 数学/逻辑类 +5~20% |
| **自洽性 Self-Consistency** | 同一问题采样 N 次（temperature 0.7），投票选答案 | +3~8%，最便宜的"显著提升" |
| **上下文压缩** | 长文档先让模型摘要/抽取相关片段，再回答 | 省 token + 降幻觉，长文本必备 |
| **少样本示例自生成** | 用模型自己造 3~5 个示例并筛选 | 接近轻量微调效果 |
| **负面指令/反例** | 明确"不要做什么"，比只说"要做什么"更有效 | 减少跑偏 |

要点：把提示词当**可迭代资产**，用评测集 A/B 测试，而不是凭感觉改。

---

## 二、推理期计算扩展（Test-time compute）

1. **Best-of-N + 验证器**：生成 N 个候选，用规则/打分模型/单元测试筛选。代码任务用"跑测试"当验证器，效果立竿见影。
2. **自检/反思（Self-Critique）**：让模型产出后自己列问题并修正，或外接一个便宜模型做 critic。
3. **任务分解**：Planner 把复杂任务拆子任务，逐个解决再汇总（Map-Reduce 思路）。
4. **多智能体辩论 / 多视角**：不同角色独立解，再仲裁。成本翻倍，适合高价值低频任务。
5. **树搜索（ToT/GoT）**：显式探索多条推理分支做剪枝。贵，用于难题。

---

## 三、外部能力外挂（提升幅度通常最大）

- **RAG**：接入向量库 + 混合检索（BM25 + 稠密向量）+ 重排序（cross-encoder / LLM rerank）+ 查询改写/多查询扩展。知识更新零成本，是"不训练更新知识"的标准解。
- **工具调用 / Function Calling**：搜索、计算器、数据库、SQL、代码执行器。凡是**确定性计算和事实检索**都外包给工具，模型只做编排——这是幻觉问题最有效的根治手段。
- **Agent 工作流**：把固定流程写死在代码里（少让模型自由发挥）。**能用工作流解决的，不要用 Agent**；Agent 只处理真正不确定的决策点。
- **约束解码 / 结构化输出**：JSON Schema、grammar约束、字段校验 + 自动重试。消除格式错误类失败。
- **Schema 与校验闭环**：解析 → 校验 → 失败带错误信息回灌重试（通常 1~2 次即可）。

---

## 四、系统与成本优化（同样提升"有效性能"）

- **模型路由（Cascade）**：简单请求走小模型，难题/低置信度升级到大模型。可省 50~80% 成本且平均质量上升。
- **置信度门控**：用 logprob 一致性或"答案稳定性"判断是否升级。
- **Prefix / Prompt Caching**：固定长 system prompt + few-shot 前缀放前面复用 KV cache，长上下文场景成本可降 70%+。
- **投机解码（Speculative Decoding）**：小模型起草 + 大模型并行验证，输出**分布完全一致**，纯提速2~3 倍。
- **连续批处理、量化（INT8/FP8/AWQ）、动态 LoRA 切换**：降延迟降成本，损失精度极小。
- **结果缓存 / 语义缓存**：高频问题直接复用。

---

## 五、配套的评估闭环（没有它，前面全是盲改）

1. 建 100~500 条真实任务的评测集，含**失败用例**（不只是正常样本）。
2. 分维度打分：准确率、格式合规率、幻觉率、延迟、成本。
3. 每次改动跑一次，**回归测试**防止修一坏三。
4. 优先修"最高频的失败模式"，而非全面优化。

---

## 六、什么时候必须放弃"不训练"

以下情形，纯推理技巧收益有限，必须动模型参数：

- 需要注入**模型参数里必须记住**的领域知识/风格（非检索可覆盖）
- 需要稳定的**特定格式/行为模式**且提示词已经很长失效（→ 此时考虑轻量微调，成本远低于全量训练）
- 需要**小模型获得大模型能力**（→ 蒸馏 + 轻量微调 / LoRA）

优先级建议：**Prompt 工程 → 工具/RAG → 工作流固化 → 采样扩展 → 路由与缓存 → 最后才是轻量微调（LoRA/SFT/蒸馏）**。

---

### 一句话总结
不训练要提性能，就做三件事：**把问题写清楚（Prompt）、给它更多思考时间（推理期计算）、把脏活交给工具和检索（RAG + tools）**，再用路由和缓存把成本压住。
