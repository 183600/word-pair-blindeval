# 不训练也能大幅提升 LLM：按投入产出排序的完整打法

核心思路:**把能力放在"上下文"和"推理时计算"里,而不是放在权重里。**下面按 ROI 从高到低排列。

---

## 一、先做地基(否则后面全是空中楼阁)

| 动作 | 成本 | 收益 |
|---|---|---|
| **建评测集** | 1-2 天 | 没有它,所有优化都是自我感动。50-200 条真实样本 + 判分脚本(规则判分优先,LLM-as-judge 次之) |
| **拆分错误类型** | 0.5 天 | 幻觉 / 格式错 / 漏约束 / 推理错 / 知识缺失 —— 五类的解法完全不同,必须先归因 |

**这一步通常比任何技术手段的回报都高。**

---

## 二、提示词层面(几乎零成本,收益最确定)

1. **把"规范"写进系统提示**
   输出格式、禁止行为、边界情况处理写成显式清单。很多错误是模型"不知道规矩"而非"做不到"。

2. **少样本示例(Few-shot)**
   3-8 个精心挑选的示例 >> 描述一千字规则。示例要覆盖**边界情况和失败模式**,不要只给happy path。
   - 反例往往比正例更有效:给出错误示例 + 修正后示例。

3. **思维链(CoT)**
   对推理类任务强制显式推理。进阶:
   - **自洽性(Self-Consistency)**:采样 k=5~20 次,投票/取多数。数学、逻辑类任务 **+10~30%**,是性价比最高的单项技术。
   - **Self-Critique / Reflection**:先生成,再让模型按 checklist 自查并改写,循环1-3 轮。

4. **XML/分隔符隔离指令**
   提示词里用 `<instructions> <examples> <query>` 包裹,降低指令与数据的混淆(尤其对弱模型)。

5. **预填充(Assistant Prefill)**
   直接以 `{"` 或 `答案是:` 开头,强行把模型拉进正确格式轨道。**格式合规率能从 60% 提到 95%+**。

---

## 三、上下文工程(Context Engineering)

这是2025 年真正的核心命题——**上下文窗口就是新的"权重"**。

- **长上下文 ≠ 好上下文**。塞100k 垃圾进去,准确率反而下降(中间迷失 / lost-in-the-middle)。
- **上下文压缩与摘要**:多轮对话做滚动摘要;大文档先让模型抽取相关部分再进主提示。
- **动态注入状态**:把当前的中间结果、已确认事实、约束清单作为变量每轮重新注入,而不是指望模型记住。
- **位置策略**:最关键的指令放**开头和结尾**( primacy + recency ),中间放数据。
- **子上下文 / 分层**:复杂任务让模型先用工具检索子模块,而不是一次性吞全部。

---

## 四、RAG(把"参数内知识"换成"可更新知识")

没有 RAG 就谈不上可维护的知识型系统。

**低成本高质量 RAG 清单:**
- 混合检索:**BM25(稀疏)+ 向量(稠密)** 召回,再融合 —— 纯向量在精确词、编号、缩写上失效
- **重排序(Cross-Encoder Rerank)**:召回 50 → 精排取 top 5~10,这是准确率提升最明显的一环- 查询改写 / HyDE / 多路查询扩展
- 给每段加**引用编号**,强制模型标注来源,可溯源即约束幻觉
- 拒答机制:检索不到就明确说"知识库无此信息",而不是编---

## 五、工具与外部能力(用代码替代模型能力)

模型最弱的领域是**精确计算、大规模检索、多步状态管理**。把这类活交给工具,准确率提升是数量级的。

- **计算/数据处理**:让模型写并执行代码(Python/SQL),而不是心算
- **精确查询**:数据库、API、搜索引擎
- **确定性函数**:格式转换、单位换算、schema 校验
- 工具描述要写清楚**什么时候该用、什么时候不该用**,并给示例

**能用工具解决的,就不要靠提示词硬掰。**

---

## 六、推理时计算扩展(Test-Time Compute)

不训练,把算力花在推理阶段:

- **Best-of-N +评估器**:生成 N 个候选,用规则/打分模型/verifier 选最优(N=5~10 通常已饱和)
- **树搜索类**:ToT / 多路径探索,适合结构化问题
- **Verifier 模式**:训练不动也能用现成小模型或规则做打分器
- **分解(Decomposition)**:复杂任务拆成子任务,每步独立验证再组合
- **多智能体(轻量)**:不同角色/不同提示词的模型互审或辩论。对可验证任务收益递减,**对开放式写作可能有害**(容易趋同),别神化
- **预算控制**:简单问题走快路径(小模型/低思考预算),难题才升级(困难度分类器)

## 七、解码与输出约束(成本几乎为零)

| 参数 | 建议 |
|---|---|
| 温度 | 结构化/抽取 **0~0.2**;创作0.8~1.0;多采样时 >0.7 保证多样性 |
| top_p / top_k | top_p=0.9 常用;必要时用 **min_p** 更稳 |
| 重复惩罚 | 长文本生成时 1.05~1.15,过高会破坏语法和代码 |
| **结构化输出** | JSON Schema / 正则 / 语法约束解码(constrained decoding)。**这是最可靠的"零训练"对齐手段** |
| Stop sequence | 防止模型续写模仿样本 |

用 constrained decoding 能做到**100% 格式合法**,不需要任何训练或提示词祈祷。

---

## 八、延迟与成本优化(让上面这些花得起)

- **Prompt Caching(前缀缓存)**:把长不变的 system prompt + few-shot 放前面,内容稳定 → 缓存命中率80%+,成本降 5-10 倍。**这是省钱第一杠杆。**
- **投机解码(Speculative Decoding)**:小模型草稿 + 大模型验证,**输出完全一致**,吞吐 2-3 倍
- **量化**部署(int4/int8)降低显存与成本
- **批处理** + 动态并发
- **KV Cache 复用**、会话前缀共享
- **模型路由/级联**:简单请求给小模型,只有难题升级;先用小模型 + 规则校验,失败再升级大模型 —— 成本可降 50-90%
- **压缩上下文 + 摘要**减少 token

---

## 九、系统层"脚手架"(Scaffold)

把 LLM 放进一个工作流里,而不是裸调用:

```
输入 → 分类(难度/类型)
 → 路由(是否需要检索?是否需要工具?用多大模型?)
     → RAG 检索 + 重排
     → 生成(N 个候选 / 反思循环)
     → 校验(规则/schema/verifier)
     → 不通过 →反馈重试(带具体错误信息)
     → 输出
```

**关键技巧:重试时把具体错误回灌**("你上次输出的 JSON 缺少 `date` 字段"),比简单地说"请修正"有效得多。

## 优先级执行清单

**第 1 周(必做,几乎免费)**
1. 建100 条评测集 + 自动化判分
2. 报错因分析
3. 精修系统提示 + 3-8 个含反例的 few-shot
4. 开 structured output / constrained decoding
5. 温度调优

**第 2-4 周**
6. RAG + 混合检索 + rerank
7. 引入工具(计算、查询、校验)
8. 上下文压缩与动态注入
9. Prompt caching 降低成本

**第 2 个月**
10. Self-consistency / Best-of-N
11. 反思与自校验循环
12. 级联路由 + 投机解码降本

**预期收益参考**:1-4 项通常带来20-40% 的可用性提升;5-9 项让成本下降 50-90% 同时质量持平;10-12 项在推理类任务上再带来 10-30%。**在不训练任何权重的前提下,端到端 2-3 倍的实际效果提升是完全现实的。**

---

## 什么时候才真的需要训练

如果做到了上面所有,还剩下:
- **稳定的行为/风格/领域术语**需要固化 → LoRA(几百美元级,不是"从零训练")
- **需要压缩成本做端侧部署** → 蒸馏小模型
- **领域知识频繁变动且必须内化** → 优先考虑继续做 RAG,这比训练便宜几个数量级

**一句话总结**:先评测,再上下文,再工具,最后才是权重。
