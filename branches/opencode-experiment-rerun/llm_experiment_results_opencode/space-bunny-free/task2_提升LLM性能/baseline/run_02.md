# 不训练模型，大幅提升 LLM 性能的方法论

核心认知：**现代 LLM 的能力有很大一部分是"没被用出来"，而不是"没有"**。测试时计算扩展（test-time compute）+ 上下文工程（context engineering）+ 解码约束，是目前性价比最高的三大杠杆。

---

## 一、先做这一步：建评测闭环（否则一切优化都是盲猜）

没有评测集，任何"优化"都无法证明有效，而且极易改好一个任务、改坏五个任务。

- 收集 100~300 条真实业务样本，人工标注期望输出（或用最强模型做 judge 基准）
- 用 LLM-as-a-Judge 打分（准确率、格式合规率、幻觉率、拒答率分别统计）
- **每次改动跑一遍**，用指标说话，避免"感觉变好了"

---

## 二、Prompt 工程（收益最高、成本最低，通常 +10~40%）

按投入产出排序的技巧：

| 技巧 | 说明 |
|---|---|
| **角色 + 任务边界** | "你是XX领域专家，只依据给定资料回答，资料不足时说不知道" |
| **正例 + 反例（Few-shot）** | 3~5 个精心挑选的样例，比抽象描述有效得多；样例要覆盖边界情况 |
| **显式评分标准** | 让模型自己按 rubric 逐项检查，比"请认真一点"有效 |
| **禁止项显式化** | 直接列出"不要写什么"，比只说"要什么"更能消除模型默认行为（如 AI 味、过度免责声明） |
| **输出格式先定义** | 先给模板再生成，减少后续解析失败 |
| **拆解大任务** | 长 prompt 分为"理解→规划→执行→校验"四段，每段独立优化 |

**动态 Few-shot**：检索与你当前 query 最相似的历史成功案例注入 prompt，效果通常远超固定 few-shot，且无需训练。

---

## 三、上下文工程（Context Engineering）

这是当前最被低估的提升手段。

1. **RAG 质量决定一切**
   - 混合检索（BM25 + 向量）召回
   - **Rerank 模型重排**（这一步通常带来最大单点提升，+15~30%）
   - Query 改写 / 多查询扩展 / HyDE（先让模型生成假设答案再检索）
   - 按相关性组装上下文，**去掉 top-k 里明显无关的内容**（噪声比缺内容更伤）

2. **位置策略**：模型对上下文首尾更敏感（"lost in the middle"）。把最关键的指令放最前/最后，中间放参考资料。

3. **上下文压缩**：长文档先做 map-reduce 摘要再注入；同时利用 **Prompt Caching**（前缀复用），缓存静态部分可省 50~90% 成本。

4. **长上下文的替代方案**：不要把10 万字全塞进去，先检索/摘要成 5 千字，往往效果更好、成本更低、延迟更低。

---

## 四、解码层面（Test-time compute）

- **Temperature / Top-p调优**：事实类任务降到 0~0.3；创意类 0.8+。这个默认值往往是最差的- **Chain-of-Thought**：推理任务必须显式要求"先思考再回答"，并禁止直接给答案
- **Self-Consistency（自一致性）**：同一问题采样 N 次（temperature>0）投票取多数。数学/推理类 **+10~25%**，是性价比最高的单一技术
- **Best-of-N +验证器**：采样 N 个答案，用规则或打分器选最优
- **Refine 循环**：生成 → 自评 → 修改，可迭代 2~3 轮
- **Logit 约束解码**：当输出必须匹配 JSON Schema / 正则 / 语法时，**用 constrained decoding 在解码层强制**，比事后解析可靠得多，能把格式合规率拉到 100%

⚠️ 注意：CoT 不是越长越好。过长的思维链会增加幻觉和错误累积，需要在 prompt 中约束"只写必要步骤"。

---

## 五、外部工具与 Agent（能力扩展的真正来源）

模型本身不该做它不擅长的事：

- **算术/精确计算** → 调代码解释器或 calculator（消除所有数值幻觉）
- **实时/私域知识** → 调搜索或数据库 API
- **结构化数据操作** → Function Calling + SQL/API
- **超大规模遍历** → 让模型生成代码去跑，而不是让它逐条"看"

**多步分解 + 工具循环**，通常比让模型一次性回答复杂任务准确率高 20~40%。同时给它**失败重试与错误信息回传**的机制。

---

## 六、模型编排（不加训练也能"组合"出更强能力）

- **级联路由**：简单问题（分类、短摘要、格式转换）用小模型，难题才走大模型。成本可降 60~80%，且不损质量
- **模型集成（Ensemble）**：同一任务跑2~3 个不同模型/不同 prompt 变体，用投票或 judge 融合- **交叉验证**：一个模型生成、另一个模型挑错（Generator-Critic 模式），能显著降低幻觉
- **用强模型造数据 +固定大 Prompt**（非训练）：把强模型的高质量答案作为 few-shot 示例或作为 judge 标准，等价于"把强模型的能力蒸馏进流程"

---

## 七、成本控制（避免提升质量却烧钱）

|手段 | 效果 |
|---|---|
| Prompt Caching | 长 system prompt 成本降 70%+ |
| 路由到小模型 | 整体成本降 50~80% |
| 批量 API（Batch API） | 离线任务成本降 50% |
| 语义缓存 | 相似 query 直接命中，命中率高的场景降 40%+ |
| 限制 CoT 长度 / 输出 token 上限 | 直接减少 token 消耗与跑题 |
| 去掉冗余上下文 | 少塞无关文档 = 又省钱又提质 |

---

## 八、优先级建议（按 ROI 从高到低）

```
1. 建评测集 + 指标 ← 前置条件
2. 调 temperature/top_p + 显式 CoT
3. Prompt 重写（角色/边界/反例/格式）
4. 输出约束解码（Schema/正则）
5. 接工具（计算器/搜索/SQL）
6. RAG 加 rerank + 去噪 + 动态 few-shot
7. Self-Consistency / Best-of-N
8. Agent 流程 + 反思校验
9. 多模型级联路由 + 缓存（成本优化）
```

**预期量级**：对知识问答/检索类任务，做到第 6 步通常能拿到 30~60% 的提升；对推理类任务，做到第 7 步通常有 15~25% 的提升；而训练一个专用模型往往还达不到这个水平。

---

## 常见坑

- ❌ 只改 prompt 不建评测，改完不知道好没好
- ❌ 盲目加 few-shot，样例质量差反而拉低效果
- ❌ RAG 只堆 top-k 不做 rerank 和去噪
- ❌ 用强模型 judge弱模型时 judge 本身有偏（位置偏好、长度偏好），需做校准
- ❌ 把"上下文越多越好"当铁律，噪声会主动伤害性能

一句话总结：**别改权重，改"喂什么、怎么解码、能不能调工具、能不能验证"——这四件事的杠杆远大于微调。**
