# 不训练模型，大幅提升现有 LLM 性能

核心思路:**性能提升 90% 来自"模型外围的系统工程"**,而不是权重本身。下面按投入产出比排序。

---

## 一、Prompt 层(零成本,收益最大)

| 技巧 | 做法 | 典型提升 |
|---|---|---|
| **结构化提示** | 角色 + 任务 + 约束 + 输出格式 + 示例,用分隔符/XML 包裹 | 10-30% |
| **少样本示例 (Few-shot)** | 3-8 个精心挑选、覆盖边界case的示例,比纯零样本强很多 | 20-50% |
| **思维链 (CoT)** | "分步骤思考后再回答";复杂推理任务必备 | 推理任务 +30-100% |
| **自洽性 (Self-Consistency)** | 采样 k=5-10 次投票/取多数,配合温度0.7 | 数学/推理 +10-20% |
| **自我批判 (Critique & Revise)** | 让模型自己检查错误并重写一遍 | 事实准确性 +5-15% |
| **负向约束** | 明确"不要做什么",比只说"要做什么"更有效 | 减少跑偏 |
| **上下文重述** | 长对话中定期让模型总结当前状态,防"迷失在中间" | 长任务 +20% |

**关键点**:Prompt 应该像写"JD 文档"一样版本化管理(类似 system prompt 的 A/B 测试),而不是随手改字符串。

---

## 二、上下文工程 (Context Engineering)

这是目前提升最大的杠杆,比 prompt 本身更重要。

**1. RAG 检索增强**
- 分块策略:语义分块 > 固定长度;保留标题层级
- 混合检索:BM25(关键词)+ 向量(语义),用 RRF 融合
- **Reranker 交叉编码器重排**(可用小模型,如 bge-reranker,极便宜)→ 提升明显
- 查询改写 / HyDE(先用模型生成假设答案,再去检索)
- 上下文里给编号引用,强制模型标注来源,便于校验幻觉

**2. 上下文压缩**
- 丢弃检索结果中不相关的片段(小模型做过滤)
- 历史对话摘要化 + 保留原始数据在外部存储,按需检索
- Prompt 压缩:用模型把长 system prompt 压缩成摘要

**3. 注意力引导**
- 把最关键的信息放在**开头和结尾**(中间容易被忽略)
- 明确写"以下是参考资料,请仅依据此回答;资料不足则说不知道"

---

## 三、推理参数调优(完全免费)

- **Temperature**:抽取/分类=0;创意=0.8-1.0;代码=0-0.2;自洽性采样=0.7-1.0
- **Top-p / Top-k**:top_p=0.9 平衡;需要多样性时调高
- **Max tokens + 停止符**:防止截断导致答案残缺(高频 bug!)
- **Stop sequences / JSON mode / 结构化输出**:减少解析失败
- **Prefix caching / Prompt caching**:固定前缀(系统提示+few-shot)放前面,可省 50-90% 成本并降低延迟

---

## 四、解码与推理加速(不改变质量,降低成本)

- **量化 (GPTQ/AWQ/INT8/INT4)**:显存降 2-4 倍,吞吐2-5 倍,质量损失 <2%
- **Speculative Decoding 投机解码**:小模型起草 + 大模型并行验证 → 2-3 倍速度,输出**完全一致**(零质量损失)
- **KV Cache 复用**:多轮对话、前缀共享场景必开
- **连续批处理 / vLLM / SGLang**:部署侧吞吐提升数倍
- **提前退出 (Early Exit)**、**稀疏 MoE 路由**

> 如果瓶颈是"慢"而不是"笨",先做这层,性价比极高。

---

## 五、编排层:小模型 + 大模型协作

**模型路由 (Routing)**:不是所有请求都需要最强模型
```
请求分类 → 简单/常见 → 小模型(7B/14B)
             → 复杂/高价值 → 大模型
```
- 典型可省 **50-80% 成本**,大模型处理量减少,整体质量还可能上升(难题被路由过去了)
- 难点任务先用小模型试,失败再升级(级联)

**级联架构**:大模型生成 → 小模型/规则做验证 → 不过则重生成
**Verifier / 规则校验**:数学用计算器、代码用执行测试、格式用 JSON schema 校验

---

## 六、工具与外部能力(通常提升最大)

给模型"外挂",把参数化知识换成可调用能力:

- **代码执行器**:数学计算、数据处理、图表、沙箱执行
- **RAG / 搜索 API**:实时知识,消除幻觉
- **函数调用**:让模型与数据库、业务系统交互
- **API 编排成 MCP 工具生态**,统一接入> 判断标准:如果任务需要精确/实时/计算,就用工具,而不是靠模型"回忆"。

---

## 七、Agent脚手架 (Scaffolding)

- **ReAct 模式**:思考 → 行动 → 观察 → 循环
- **Plan-and-Execute**:先拆解计划,再逐步执行(适合长任务)
- **反思机制**:执行后自我检查、修正
- **多智能体分工**:规划者 / 执行者 / 审查者(注意:并非所有场景都优于单智能体,简单任务别上)
- **Todo/状态管理**:显式维护任务清单,避免跑偏

---

## 八、防幻觉与质量保障

1. **Grounding**:答案必须引用检索片段编号
2. **拒答机制**:给出"无法确定"路径,置信度低的显式标注
3. **LLM-as-a-Judge**:用更强模型或不同模型做评测(注意位置偏差和自我偏好)
4. **黄金集评测**:建 100-300 条真实业务用例,每次改动跑回归,避免"改好一个坏三个"
5. **规则兜底**:关键字段用正则/枚举校验

---

## 落地路线图(建议顺序)

```
第1周  : Prompt/参数系统化 + 结构化输出 + 停止符修复第2周  : RAG 基础链路 + Reranker + 引用溯源
第3-4周:工具调用(搜索/代码执行) + 模型路由 + 缓存量化
第2月  : Agent 编排 + 验证器 + 评测体系持续迭代
```

---

## 关键认知

1. **先评测,再优化**。没有评测集,一切优化都是玄学。
2. **区分两类问题**:"模型不知道"→ RAG/工具;"模型不听话"→ Prompt/约束/验证。
3. **别用最强模型掩盖工程问题**。系统优化后,7B 模型常常能打平优化前的 70B。
4. **成本优化不是降模型,而是"该省的省、该用的用"**。
5. 微调解决的是**风格和格式**问题,知识问题永远靠 RAG/工具。

---

## 一句话总结

> **不训练的前提下,性能提升公式 = 好的上下文(RAG/工具) × 好的推理引导(CoT/Few-shot) × 好的编排(路由/验证) × 好的评测闭环。**
> 优先做前三项,通常能拿到 2-5 倍的端到端效果提升,而额外成本可以做到接近零。
