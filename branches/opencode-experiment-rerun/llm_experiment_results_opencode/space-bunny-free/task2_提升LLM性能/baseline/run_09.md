# 不训练模型，大幅提升现有 LLM 性能的方法

核心思路：**模型能力是固定的，但"模型被怎样调用"是可以被工程化的**。下面按性价比从高到低排列。

---

## 一、提示工程层（成本最低、收益最大）

### 1. 结构化系统提示（把隐性规则显式化）
把散落在人脑里的业务规则、边界条件、输出规范，全部写成 LLM 能遵守的规则清单。

- 用**角色 + 任务 + 约束 + 输出格式 + 示例**五段式- 明确写"不要做什么"（负向约束往往比正向指令更有效）
- 把规则**编号**（`规则3：金额超过1万需标记审批`），便于后续溯源和调试

> 实测：仅把一段模糊 prompt 改写成带编号规则和反例的 prompt，效果常常相当于换了个更强的模型。

### 2. Few-shot（示例是最便宜的"免训练微调"）
- 示例数量 3–8 条，通常超过 8 条收益递减
- **示例要覆盖边界情况**，不只覆盖典型情况（加1–2 条"错误示范 → 正确改写"）
- 示例的**标签分布要贴近真实输入分布**，否则会造成偏置
- 选择示例的逻辑：按语义相似度动态检索（kNN选 few-shot），比固定示例强很多

### 3. 思维链（CoT）与自我一致性
- 复杂推理任务：强制"先分析再输出结论"，中间步可以用固定模板
- **Self-Consistency**：同一问题采样 N 次（temperature 0.7–1.0）走不同路径，取多数答案，能显著提升数学/逻辑类准确率
- **程序化 CoT**：能转成代码/公式的推理，直接要求模型输出代码并执行，用解释器结果代替 LLM 的算术（LLM 算数很弱，工具很准）

### 4. Prompt 压缩与去歧义
低成本的"提示优化"三板斧：
- 删除冗余词、缩短上下文 → 降成本 + 降干扰
- 消除多义词、指代不明
- 给抽象词下明确定义（模型对术语的理解常与人不同）

---

## 二、上下文工程（Context Engineering）

### 5. 上下文预算分配
上下文不是越长越好。注意力是有限资源，**塞太多无关内容会挤掉关键信息**（"迷失在中间"现象）。

有效做法：
- 把最重要 instructions 放在**开头和结尾**（中间最容易被忽略）
- 长文档前做**递归摘要 / 分块摘要**，而不是原文堆叠
- 定期做**上下文裁剪**：把已完成的对话历史压成摘要，只保留目标、已定决策、未解决项

### 6. 生成"外部记忆"（把状态从模型里挪出来）
Agent 场景里，把对话摘要、当前进度、已做决策写进 prompt 每轮重新拼装，而不是指望模型记住。这就是让长任务不跑偏的关键。

---

## 三、检索增强（RAG）——最典型的"不训练提性能"

RAG 把"参数里的知识"换成"检索来的知识"，是**用工程换参数**最成功的范式。

### 关键优化点（按影响排序）
| 环节 | 优化手段 |
|---|---|
| 分块 | 按语义/标题切分，父子块（小块检索+大块喂给模型），避免一刀切固定长度 |
| 嵌入 | 领域不通用时，**训练一个轻量 embedding 模型**（几百万级文本即可，不是训练 LLM） |
| 召回 | **混合检索**：向量 + BM25/关键词；再叠加 query 改写/多路 query 扩展 |
| 重排 | 上 Cross-Encoder reranker（可用小型开源模型，CPU 也行），Top-50→Top-5 精确率提升非常明显 |
| 生成 | 要求"仅依据给定资料回答，资料不足时说不知道"，附引用来源 |

### 少有人注意的高价值技巧
- **Rerank 是性价比最高的单点优化**，通常比换更好的生成模型收益更大
- 加一个 **"检索结果 → 判断是否够用 → 不够则改写 query 再检索"** 的循环，2轮通常就有明显提升
- 少样本 + rerank +引用约束，三者叠加效果远超单点

---

## 四、解码与采样控制（被严重低估）

不改模型也能改输出分布：

- **Greedy（temperature=0）** 用于确定性和抽取类任务，比高温采样准确率高
- **分类/意图识别任务**：不要用自由文本，改成**选项打分**——让模型给 A/B/C/D 打分或输出 logprob 选最大，比生成再解析稳定得多
- **结构化输出**：用 JSON Schema / Grammar约束解码（vLLM、Outlines、lm-format-enforcer），消除格式解析失败
- **Beam search / 低温度 +多次采样投票**
- **停止序列 + 长度上限**做截断控制，避免废话和不完整输出
- **限制 token预算**：给每个子任务单独设 max_tokens，防止一处超长拖垮整体

---

## 五、工具调用与外部能力外挂

这是**成本最低的"能力跃升"**：LLM 不擅长的事，交给确定性的东西。

1. **计算** → Python / 计算器
2. **查证/时效知识** → 搜索 API
3. **精确匹配/查库** → SQL / 内部 API
4. **格式转换** → 代码化处理
5. **MCP（Model Context Protocol）**：把内部系统封装成标准接口，模型自动调用，免训练接入

关键设计原则：**LLM 负责意图理解和决策，工具负责执行和精度**。让模型"写代码并运行"比"用心算"可靠几个数量级。

---

## 六、编排与架构（用系统级设计补模型缺陷）

### 1. 任务分解（Decompose）
复杂任务拆成多个**单一职责**的小调用，每个 prompt 都更简单、准确率更高。
- 常见模式：Plan → Execute → Verify → Revise
- 或"草稿 → 批判 → 改写"（Critic 模式，用同一个模型换角色即可，无需额外训练）

### 2. 多模型路由（Model Routing）
不同子任务用不同模型，别拿最贵的模型干所有的活：
- 意图分类、格式转换 → **小模型（0.5B–8B）甚至规则**
- 常规生成 → 中等模型
- 难题 / 评审 → 大模型

这样**总成本下降、准确率上升**。

### 3. 结构化校验 + 自动重试
输出 schema校验、字段范围校验、正则校验，失败自动带着错误信息重试 1–2 次。
**这是投入产出比最高的可靠性工程手段。**

### 4. 多智能体/辩论
让多个角色（生成者/批评者/裁判）互相校验，对判断类任务有增益。但注意：**不是所有任务都适合，Agent 数量≠性能**，容易陷入"多错相错"。

---

## 七、推理基础设施优化（降本 + 提吞吐）

- **量化**（INT8/INT4、GPTQ/AWQ/FP8）：几乎无损降本，但**不要指望它提准确率**，它的价值在速度和成本
- **Prefix Cache / Prompt Cache**：系统提示和 few-shot 复用，缓存命中可省 90%+ prefill 成本
- **批处理 + 连续批处理**：吞吐提升数倍
- **投机解码（Speculative Decoding）**：小模型草稿+大模型验证，**无损加速 1.5–3 倍**，是真正"免费"的性能提升
- **语义缓存**：相似问题直接命中缓存结果
- 长上下文可用 prompt压缩模型（LLMLingua）省钱

---

## 八、输出后处理（最容易被忽略）

模型输出质量 ≠ 最终交付质量：

- 规范化（去重、排序、清洗）
- **再做一次"廉价校验"**：规则/正则/小模型判别
- 不合格自动回退到兜底方案
- **黄金集回归测试**：任何 prompt 改动都跑一遍，防止改好一个坏三个（这是 prompt 工程最大的隐性成本）

---

## 九、不训练也能做的"轻量适配"

如果确实想调模型行为但不想做大规模训练：

- **LoRA / PEFT**：只训百万级参数的适配器，训练成本比全量低1–2 个数量级，几小时即可产出
- **In-Context Learning + 示例选择器**：本质上的"免训练学习"
- **Prefix / System Prompt 模板化 + 自动化搜索**：把 prompt 模板当超参，用贝叶斯优化/进化算法自动搜索最优 prompt
- **Prompt 蒸馏**：用大模型生成高质量标注 → 训练小模型跑线上（这是真正降本的关键路径）

---

## 优先级清单（如果你只有一周）

1. **重写系统提示**：结构化 + 编号规则 + 明确负向约束
2. **加 few-shot，尤其是边界案例**
3. **接入 RAG + rerank**（如果涉及外部知识）
4. **关键任务接工具**（算数、查库、搜索）
5. **结构化输出 + schema 校验 + 自动重试**
6. **多模型路由**（小模型做分类，大模型做难题）
7. **建黄金测试集**，把上面每一步都量化验证

---

## 诚实的边界

必须说明：这些方法能解决的是**"模型能力未被充分利用"**的问题，无法解决**"模型能力本身不够"**的问题。

- ✅ 格式不稳定、指令遵循差、幻觉、知识缺失、缺领域适配 → 工程手段很有效
- ❌ 极难推理前沿（复杂多步数学、代码深层调试）、需要最新实时知识、需要精确长程规划 → 上限有限- 当工程手段榨干后（通常会经历一个陡峭上升期），**唯一出路是训练（LoRA 或全量）或换更强的基础模型**

> 一句话总结：**把 prompt 当代码写，把上下文当内存管理，把工具当执行器，把测试当 CI——LLM 的上限很大程度是被"用法"限制住的，而不是被参数量限制住的。**
