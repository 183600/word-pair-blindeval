# 不训练模型，大幅提升 LLM 效果：可落地的完整方案

核心思路：**能力不来自权重，而来自"输入的上下文" + "推理时花更多算力" + "外部工具/知识"**。下面按 ROI 从高到低排。

---

## 0. 前提：先建评测集，否则一切优化都是盲改（必做，1 天）

没有测量就没有提升。建议：

- 收集 100~500 条真实线上样本，人工标注期望输出/打分维度（正确性、完整性、格式合规、是否拒答）
- 固化一个 `eval.py`：批量跑、算分、对比不同版本（prompt / RAG / 模型），指标可回归
- 做**错误分类**（错知识？错格式？漏步骤？幻觉？还是模型根本不具备该能力？）——这一步决定后面该投哪一项

> 经验：80% 的"模型不行"其实是 prompt 或上下文问题，只有 5~10% 是模型能力上限问题。

---

## 1. Prompt 工程（ROI 最高，几乎零成本）

### 关键手法

**(a) 角色 + 任务边界 + 硬约束**
```
# 角色
你是 XX 领域的资深专家，擅长……

# 任务
根据下面的输入，输出 XXX。

# 规则（硬约束，必须遵守）
1. 只使用 <资料> 中的信息，不得编造
2. 输出必须为 JSON，符合以下 schema：{...}
3. 信息不足时输出 {"need_more_info": true, "question": "..."}，不要猜
4. 不要输出解释性前言，直接给结果

# 资料
{context}

# 输入
{query}
```

**(b) 思维链的"结构化"优于自由发挥**：不要写"Please think step by step"，而是写明具体步骤：
```
按以下顺序处理：
1. 抽取输入中的实体、意图、时间范围
2. 判断属于哪一类问题（分类/计算/检索/创作）
3. 若为计算类：列出已知量、公式、代入过程
4. 检查结果是否满足 <约束> 中的所有条件
5. 只输出最终答案
```

**(c) 少样本示例（Few-shot）**：3~8 个高质量样例比 100 个弱样例有效得多。覆盖：正常案例、边界案例、需要拒答的案例、容易混淆的对立案例。示例要**格式完全一致**，并在示例间写 `###` 分隔。

**(d) 反例约束**：明确列出"不要做什么"（不要编造引用、不要输出多余寒暄、不要在 JSON前后加 ```）。

**(e) 预填充（Prefill）**：让模型直接续写你的开场，如 `Assistant:` 前先写 `{"answer": "`，可100% 保证格式。

**预期收益：简单任务 +20~50% 准确率；复杂任务 5~15%。**

---

## 2. 上下文工程（决定上限）

- **信息位置敏感**：重要信息放**开头和结尾**（中间容易被忽略，"lost in the middle"）。把硬约束放最后。
- **上下文压缩/摘要**：长对话用"摘要 + 最近 N 轮 + 关键事实卡片"代替全量历史- **上下文净化**：去重复、去日志噪声、保留时间戳（对时效性判断关键）
- **动态裁剪**：只注入与当前 query 相关的片段，而不是把整个知识库塞进去（噪声 > 信息）
- **分隔符与标签化**：用 `<doc id=..>` 明确边界，同时**降低（而非提高）**注入风险——不要用 "ignore previous instructions" 这类反直觉写法

---

## 3. RAG：把"不知道"变成"查得到"（知识型任务必备）

基础 RAG 只到 60 分，要上分必须做这几步：

```
用户问题
  ↓
① 查询改写：拼写纠正 + 多查询扩展（生成 3 个不同角度的检索式）
  ↓
② 查询分解：复杂问题拆成子问题（"对比 A 和 B" → 分别检索 A、B）
  ↓
③ HyDE：先让 LLM 幻觉生成一个"假想答案"，用假想答案去检索（提升召回 10~20%）
  ↓
④ 混合检索：BM25（关键词精确匹配）+ 向量（语义），RRF 融合
  ↓
⑤ 重排序（关键！）：cross-encoder 或 LLM rerank，取 Top-3~5
  ③→⑥ 逐块"逐块回答再聚合"，避免长上下文被稀释
  ↓
⑦ 引用约束 + 不足则拒答/追问（显著降低幻觉）
```

**收益点排序（按对效果的贡献）**：
1. **Rerank**（通常 +10~20%）
2. **查询改写/分解**（+10%）
3. **HyDE**（+5~10%）
4. 混合检索（+5%）
5. 换更好的 embedding（如果预算允许）

另加两个低成本配套：
- **让 LLM 在答案里标注引用来源**，便于人工复核（幻觉率肉眼可见下降）
- **知识库治理**：去重、按版本/时效打标签、过期内容自动降权

## 4. 工具调用 / 函数调用 / 代码执行

让模型**不算，只做选择和编排**。这是最容易被忽视的性能杠杆：

| 工具 | 解决什么 |
|---|---|
| Python/SQL 代码执行 | 数学计算、统计、字符串处理 —— 精确率从 90%→100% |
| 搜索/浏览器 API | 实时知识、时效问题 |
| 数据库 / API 查询 | 避免幻觉出具体数字和 ID |
| 专用小模型 | 分类、NER、抽取任务交给小模型（更准 + 更便宜） |

> 原则：**能用确定性代码做的，绝不交给 LLM 生成**。日期计算、单位换算、排序去重，全部用代码。

## 5. 测试时计算扩展（Test-Time Compute）—— 不训练也能"变强"

同一个问题问多次，用算力换准确率：

**(a) 自洽性（Self-Consistency）**
```python
# 生成 N 次（temperature=0.7~1.0），对 CoT 中的最终答案做投票
answers = [llm(prompt, temp=0.8) for _ in range(8)]
final = majority_vote(extract_final_answer(answers))
# 配合结构化输出，投票准确率通常 +5~15%
```

**(b) Best-of-N +验证器筛选**
生成 N 个候选 → 用规则/小模型/LLM-as-Judge 打分 → 取最优。
关键在于**验证信号**：规则校验（JSON 合法性、数值范围、单元测试）比"让 LLM 自己打分"可靠得多。

**(c) 反思 / 自检回路（Refine Loop）**
```
生成初答 → 用不同 prompt（"作为严格审稿人，只找错误和遗漏"）审 →带着具体缺陷清单重写 → 最多迭代 2~3 次
```
注意：**要给具体缺陷而不是"再检查一遍"**，且要限制轮数防止发散（通常2 轮最佳）。

**(d) 多模型投票 / 集成**：2~3 个不同模型（或不同风格 prompt）各出一次，投票或让一个模型做裁判聚合。

## 6. 工作流编排（Agentic Pipeline）

复杂任务不要指望一次调用解决，用固定流程代替"一步到位"：

```
意图分类 →（简单？→ 小模型直接答 / 复杂？→ 下面）
复杂路径：
  任务分解 → 并行执行多个子任务 → 结构化汇总 → 校验 →（不过则带错误信息重试）→ 输出
```

成本控制：
- 子任务**并行**调用，总延迟 ≈ max 而非 sum
- 简单子任务路由到便宜小模型
- 每步输出结构化（JSON），保证可拼接

---

## 7. 模型层面的"无损"优化

**(a) 级联路由（同时降本 + 提质）**
```
小模型先答 → 置信度评估（logprob / 自洽性 / LLM 判断）
  ≥阈值 → 直接返回
  <阈值 → 升级到大模型
```
经验可做到：**成本降 50~70%，效果持平或略升**（因为难题被正确路由了）。

**(b) 受约束解码（Constrained Decoding）**
用 grammar / JSON schema / 正则 限制采样空间（如 Outlines、llama.cpp GBNF、XGrammar）。这从机制上**消除**格式错误和非法枚举，比在 prompt 里求模型守规矩可靠10 倍。适用于分类、抽取、格式化输出。

**(c) 解码参数**
- 抽取/分类：`temperature=0, top_p=1`
- 创作/发散：`temperature=0.8~1.0`
- `min_p` 常比 `top_p` 更稳
- 长文本注意 `repetition_penalty`（但设过大会破坏代码/公式）

**(d) 缓存**
- **Prefix caching**：把长 system prompt + 固定知识放在最前并缓存，KV cache 复用 → 延迟和成本降 5~10 倍
- 语义缓存：相似 query 直接命中历史答案

**(e) 投机解码（Speculative Decoding）**：输出分布与目标模型完全一致，纯加速降本。

## 8. 自动化 Prompt 优化（无训练，只优化"程序"）

把 prompt 当成可自动搜索的参数，用 LLM 反馈当信号：
- **DSPy**（`MIPROv2` / `BootstrapFewShot`）：自动合成 few-shot 示例、自动改写指令，效果常常超过手写 prompt
- **TextGrad / APO / OPRO**：用文本反馈做"梯度"迭代 prompt

> 注意：这不需要更新模型权重，属于 prompt 级别的优化，但确实需要少量推理预算和一个小评测集。

## 避坑清单

1. **别把 prompt 越写越长**：无关规则会稀释注意力，反而变差；规则要有序、去重、可执行
2. **CoT 不是越长越好**：小模型上超长 CoT 常导致胡搅蛮缠；明确列出步骤比"think step by step"有效
3. **不要指望 prompt 修正知识错误**：模型不知道的事实，prompt 救不了 → 必须 RAG 或工具
4. **RAG 加了重排序才算数**：只堆 top-10 chunk 往往不如精排 top-3
5. **反思回路要限制轮数**（2 轮内），否则会"越改越错"
6. **温度调 0 不等于确定性**：批处理、并行计算仍会有微小差异
7. **RAG 引入注入风险**：检索到的文档必须视为数据而非指令，加输入过滤 + 输出验证
8. **每次改动都在评测集上验证**，防止"改一个好两个坏"

---

## 一句话总结

> **不训练的最优组合 = 结构化 Prompt + Few-shot + 约束解码 + 工具调用（代码执行）+ 带重排的 RAG + 自洽性/反思投票 + 小模型级联路由。**
> 前三项一周内可落地、见效最快；后三项决定天花板。先测量，再按错误类型优先投入。
